## 📋 问题背景

**项目**: 招标文件AI编制工具（JDK21 + Spring Boot 3.2.2 + MyBatis-Plus 3.5.5）

**当前状态**: AI模块 `AiTaskProcessor` 使用单线程 `@Scheduled(fixedDelay=5000)` 轮询，取最多10个PENDING任务后**顺序执行**。一个AI任务卡住，后续全部等待，导致任务超时。

**涉及组件**:
- `ele-ai-tender-ai`（8083端口）：AI任务处理模块
- `ele-ai-tender-support`（8080端口）：支撑中心，管理系统参数
- `sup_sys_parameter` 表：已有分组参数管理机制（SYSTEM/SWITCH/AI_RULE）

---

## 🔴 核心问题

- `AiTaskProcessor` 顺序执行AI任务，无并发能力
- 无用户级并发控制，单用户可占满所有资源
- 无任务超时机制，卡死任务阻塞队列
- 线程池参数写死，无法运行时调整

---

## 🎯 实现目标

1. 动态线程池，参数存DB，运行时热更新不重启
2. 用户级并发控制：每用户最多发起N个任务（超限直接拒绝），同时执行M个（超限排队等待）
3. 全局并发控制：同理
4. 单任务超时控制
5. 参数通过支撑中心后台管理界面修改

---

## 🔧 技术约束

- 参数复用 `sup_sys_parameter` 表（`AI_THREAD_POOL` 分组）
- 热刷新链路：support修改参数 → HTTP通知AI模块 → AI模块重新读DB刷新
- 不引入外部依赖（Hippo4j/DynamicTp等），自研轻量方案
- AI模块参数不走Redis缓存（参考 ModelConfigCacheService 直接查DB），保证实时生效
- 刷新端点必须在 `/api/` 路径下，受JWT认证保护
- JDK21环境，编译必须设置 `JAVA_HOME=D:/Users/admin/.jdks/openjdk-21.0.5`

## ✅ 最终方案

### 参数模型（`param_group = AI_THREAD_POOL`，9个参数）

| param_key | 默认值 | 含义 |
|-----------|--------|------|
| `ai_core_pool_size` | 4 | 核心线程数 |
| `ai_max_pool_size` | 8 | 最大线程数 |
| `ai_queue_capacity` | 20 | 队列容量 |
| `ai_keep_alive_seconds` | 60 | 空闲线程存活时间 |
| `ai_task_timeout_minutes` | 10 | 单任务超时时间 |
| `user_max_pending_tasks` | 5 | 每用户最多发起任务数 |
| `user_max_concurrent_tasks` | 2 | 每用户同时执行任务数 |
| `global_max_pending_tasks` | 100 | 全局最多发起任务数 |
| `global_max_concurrent_tasks` | 10 | 全局同时执行任务数 |

### 核心架构

```
支撑中心后台修改参数
  → SysParameterServiceImpl.updateByKey()
  → ThreadPoolConfigNotifier 检测 AI_THREAD_POOL 组变更
  → InternalAiServiceClient HTTP POST /api/v1/threadpool/refresh
  → DynamicThreadPoolManager.refresh() + UserConcurrencyManager.refresh()
```

### 任务提交流程（修复了竞态条件）

```
poll() → 取PENDING任务
  → tryReserve(userId) 查DB统计，发起数超限→标记FAILED
  → tryAcquire(userId) Semaphore非阻塞，并发数满→保持PENDING排队
  → CAS PENDING→PROCESSING，失败→release许可
  → submit到线程池 → Future.get(timeout) → finally release
```

### 关键设计决策
- 发起数统计：查 `ai_task` 表 `COUNT(*) WHERE create_id=? AND status IN ('PENDING','PROCESSING')`
- 并发数控制：Semaphore（用户级 + 全局级双层）
- Semaphore热刷新：`new Semaphore(max - currentActive)` 保留活跃计数
- 先 tryAcquire 再 CAS：避免 PROCESSING→PENDING 状态弹跳
- batchUpdate 统一通知一次：避免9次重复刷新

## 🐛 已知问题和待解决

### 审查发现但未修复的P2问题

1. **H4: SSE Chat无并发限制** — `AiChatServiceImpl` 的 streamChat/streamOptimize 绕过了 UserConcurrencyManager，用户可大量发起SSE请求耗尽线程池。建议加 RateLimiter。
2. **M2: 参数无校验** — DB中配置 `ai_core_pool_size=0` 会导致 ThreadPoolExecutor 构造失败。建议在 `loadFromDb` 中加范围检查。
3. **C2: Future.cancel(true)不保证中断** — AI任务（HTTP调用大模型）可能不响应中断，超时后任务继续运行但Semaphore已释放。建议在 dispatch 内部检查 Thread.interrupted()。
4. **H3: 线程池重建时可能 RejectedExecutionException** — execute/submit 直接读 volatile executor 引用，refresh 期间可能提交到已 shutdown 的旧线程池。建议加重试逻辑。

- JDK21 lambda 中引用的局部变量必须是 effectively final，赋值后需 `final int x = computedValue`
