## 📋 问题背景

**项目**: 招标文件AI编制工具（JDK21 + Spring Boot 3.2.2 + MyBatis-Plus 3.5.5）

AI模块 `AiTaskProcessor` 原使用单线程 `@Scheduled(fixedDelay=5000)` 轮询，取最多10个PENDING任务后**顺序执行**，一个AI任务卡住后续全部等待导致超时。需改为动态线程池并发执行。

**涉及模块**:
- `ele-ai-tender-ai`（8083端口）：AI任务处理，包含线程池和并发控制
- `ele-ai-tender-support`（8080端口）：支撑中心，管理 `sup_sys_parameter` 系统参数
- `ele-ai-tender-support-frontend`：支撑中心前端，参数管理界面

---

## 🔴 核心问题

- 顺序执行AI任务，无并发能力
- 无用户级并发控制，单用户可占满所有资源
- 无任务超时机制
- 线程池参数写死，无法运行时调整

---

## 🎯 实现目标

1. 动态线程池，9个参数存DB，运行时热更新不重启
2. 用户级并发控制：每用户最多发起N个任务（超限拒绝），同时执行M个（超限排队）
3. 全局级并发控制：同理
4. 单任务超时控制（Future.get + cancel）
5. 支撑中心后台管理界面修改参数，AI模块自动感知

## ✅ 当前方案：DB轮询Hash检测

### 设计思路

AI模块自包含，不依赖外部通知。通过 `@Scheduled` 定时轮询DB参数，计算Hash比对变更，自动刷新。

```
支撑中心修改参数 → 写入sup_sys_parameter表 → 清Redis缓存
                                              ↓
AI模块 @Scheduled(10s) → loadFromDb() → computeHash() → 比对cachedParamHash
  → Hash相同：跳过
  → Hash不同：applyRefresh() → 更新线程池 + 更新并发控制
```

### 核心机制

**1. Hash检测（DynamicThreadPoolManager）**
```java
@Scheduled(fixedDelay = 10000)
public void checkAndRefreshIfNeeded() {
    ThreadPoolProperties newProps = loadFromDb();
    String newHash = computeHash(newProps);
    if (newHash.equals(cachedParamHash)) return;
    applyRefresh(newProps);
    this.cachedParamHash = newHash;
}
```
- 9个参数值拼接 `core=4|max=8|queue=20|...` 取 `hashCode().toHexString()`
- 每次参数变更支撑中心只需正常写DB，AI模块10秒内自动感知

**2. 任务提交流程（AiTaskProcessor）**
```
poll() → tryReserve(userId) 查DB统计发起数，超限→跳过
       → tryAcquire(userId) Semaphore非阻塞获取，满→保持PENDING排队
       → CAS PENDING→PROCESSING，失败→release许可
       → submit到线程池 → Future.get(timeout) → finally release
```
- 先获取Semaphore再CAS，避免PROCESSING→PENDING弹跳

**3. Semaphore热刷新（UserConcurrencyManager）**
```java
public synchronized void refresh(ThreadPoolProperties newProps) {
    int currentGlobalActive = getGlobalActiveCount();
    int newGlobalPermits = Math.max(1, newGlobalMax - currentGlobalActive);
    this.globalSemaphore = new Semaphore(newGlobalPermits);
    this.userSemaphores = new ConcurrentHashMap<>();
}
```
- 新Semaphore = max - 当前活跃数，保证刷新后并发控制不失效

**4. 发起数统计**：查 `ai_task` 表
```sql
SELECT COUNT(*) FROM ai_task WHERE create_id = ? AND status IN ('PENDING','PROCESSING') AND is_delete = 0
```

## 🐛 已知问题和待解决

### P2 - 建议后续修复

1. **SSE Chat无并发限制** — `AiChatServiceImpl` 的 streamChat/streamOptimize 绕过了UserConcurrencyManager，用户可大量发起SSE请求耗尽线程池。建议加 RateLimiter 或独立Semaphore。
2. **参数无范围校验** — DB配置 `ai_core_pool_size=0` 会导致ThreadPoolExecutor构造失败。建议在 `loadFromDb` 中加 min/max 检查。
3. **Future.cancel(true)不保证中断** — AI任务（HTTP调用大模型）可能不响应中断，超时后任务继续运行但Semaphore已释放。建议在dispatch内部检查 `Thread.interrupted()`。
4. **线程池重建时RejectedExecutionException** — execute/submit直接读volatile executor引用，refresh期间可能提交到已shutdown的旧线程池。建议加重试逻辑。

### 关键依赖关系

```
DynamicThreadPoolManager
  ├── @Autowired SysParameterReadMapper（读sup_sys_parameter）
  ├── @Lazy @Autowired UserConcurrencyManager（避免循环依赖）

UserConcurrencyManager
  ├── @Autowired AiTaskMapper（countPendingByUserId/Global）

AiTaskProcessor
  ├── @Autowired DynamicThreadPoolManager
  └── @Autowired UserConcurrencyManager
```

### 开发心得

- DB轮询Hash检测比HTTP通知更简单可靠：无额外依赖、无网络故障点、无重复通知问题
- Semaphore热刷新需保留活跃计数：`new Semaphore(max - currentActive)`
- 先获取Semaphore许可再CAS改状态，避免PROCESSING→PENDING状态弹跳
- JDK21 lambda中引用的局部变量必须是effectively final，赋值后需 `final int x = computedValue`
- DynamicThreadPoolManager ↔ UserConcurrencyManager 循环依赖用 `@Lazy` 解决
