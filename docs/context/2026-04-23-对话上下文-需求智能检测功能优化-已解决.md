# 对话上下文：需求智能检测功能优化

> 生成时间：2026-04-23 | 状态：已解决

---

## 问题背景

**项目**：招标文件AI编制工具（tender-document-tool）
**模块**：需求级智能检测（RequirementDetect）
**涉及组件**：
- 后端：`RequirementServiceImpl`、`DetectionResultParser`、`TbDetectionRecordMapper`、`DetectionIssueVO`(ai/core)、`PromptTemplates`
- 前端：`RequirementDetect.vue`、`detection.ts`
- AI模块：4种检测器（SensitiveWord/Typo/PolicyReview/FormatCheck）

需求智能检测对业务需求内容执行敏感词+错别字两项AI检测，用户可接受/拒绝建议，接受时自动替换原文。

---

## 核心问题

### 问题1：重新检测时旧记录未清理
- **表现**：点击"重新检测"后，旧 `TbDetectionRecord` 仍在数据库中，`restoreDetectionState()` 加载全部记录导致同一检测类型出现多条记录
- **根源**：`submitDetection()` 每次创建新记录，不删除旧记录；前端 `findIndex` 匹配第一张卡片但 `parseTaskResult` 对每条记录都执行，导致 issues 重复和 recordId 错位

### 问题2：后端 VO 缺失 original 字段
- **表现**：前端 `DetectionIssueVO` 有 `original` 字段，后端 core 模块 VO 没有
- **根源**：后端 VO 设计遗漏，前端直接解析原始JSON绕过了这个问题

### 问题3：targeted 字段语义理解偏差
- **表现**：提示词新增 `targeted` 字段后，初始实现将 `targeted` 作为高亮定位文本，`suggestion` 仍作替换目标
- **纠正**：`targeted` 的正确语义是"替换原文的内容"，替代原来 `suggestion` 在自动替换中的角色；`suggestion` 降为辅助描述

### 问题4：接受建议时原文不存在无状态反馈
- **表现**：原文已被修改后，接受建议时后端仅打 warn 日志，handleStatus 仍标记为1(已接受)，用户无法感知替换失败
- **根源**：缺少"未找到"状态

---

## 实现目标

1. 重新检测时自动清理旧记录，避免重复数据
2. 前后端 VO 字段对齐，补全 `original` 和 `targeted` 字段
3. 接受建议时用 `targeted`（非 `suggestion`）替换 `original`
4. 新增 `handleStatus=3`（未找到），原文不存在时明确反馈
5. 前端展示适配四种状态 + targeted 优先展示

---

## 技术约束

- `TbDetectionRecord` 继承 `BaseEntity`，有 `@TableLogic` 逻辑删除（`is_delete` 字段）
- 软删除用原生 `@Update` SQL 绕过 `@TableLogic`，不更新 `ver/modifyTime`
- `submitDetection()` 标注 `@Transactional(rollbackFor = Exception.class)`，软删除和插入在同一事务中
- AI模块的 `DetectionIssueVO` 是独立DTO，与core模块的VO不同步
- 前端 `parseTaskResult()` 直接解析原始JSON字符串，不依赖后端VO序列化

---

## 最终方案

### 1. 软删除旧记录（后端）
- `TbDetectionRecordMapper` 新增 `softDeleteByRequirementId()` 和 `softDeleteByProjectId()`
- `submitDetection()` 在创建新记录前调用软删除
- 旧AI任务仍会执行完，但 `syncDetection` 因 `selectById` 查不到记录而跳过结果同步

### 2. targeted 字段适配（全栈）
- **提示词**（用户已修改）：4种检测类型的 JSON 示例新增 `"targeted": "修改内容(可直接替换原文)"`
- **AI模块 VO**：新增 `private String targeted`
- **Core模块 VO**：新增 `private String original` + `private String targeted`
- **DetectionResultParser**：`parseIssues()` 解析 `original` 和 `targeted`
- **RequirementServiceImpl**：`acceptDetectionIssue()` 替换逻辑 `replaceFirst(original, targeted)`
- **前端类型**：`DetectionIssueVO` 新增 `targeted: string`
- **前端 UI**：优先展示 `targeted`（标签"替换建议"），无则降级展示 `suggestion`（标签"AI建议"）

### 3. handleStatus=3（未找到）
- **后端**：`acceptDetectionIssue()` 中 `updateFlag=false` 时设 `handleStatus=3`
- **前端**：状态标签四种显式判断：`0=未处理`、`1=已接受(success)`、`2=已拒绝(info)`、`3=未找到(warning)`
- `totalUnhandledIssues` 只统计 `handleStatus===0`，3不算未处理
- `getIssueClass` 中 `handleStatus!==0` 返回 `is-handled`，3天然归类

### 4. 前端 restoreDetectionState 防御性优化
- 按 `detectionType` 分组，每种类型只取 `id` 最大的最新记录
- 使用 `Map<string, RequirementDetectionRecord>` 去重

## 使用方法

### handleStatus 状态码
```
0 = 未处理（显示接受/拒绝按钮）
1 = 已接受（success标签，后端已执行 replaceFirst(original, targeted)）
2 = 已拒绝（info标签，仅更新状态）
3 = 未找到（warning标签，原文已不存在，替换未执行）
```

### AI检测结果JSON格式（最新版）
```json
{
  "issues": [
    {
      "position": "问题位置描述",
      "original": "原文内容（查找定位）",
      "targeted": "修改内容（直接替换original）",
      "suggestion": "修改建议（辅助描述）",
      "reason": "问题原因",
      "severity": "HIGH|MEDIUM|LOW",
      "handleStatus": 0,
      "detectionType": "TYPO",
      "policyReference": "（政策审查专用）",
      "ruleViolated": "（格式检测专用）"
    }
  ],
  "score": 85
}
```

### 自动替换逻辑
```
接受建议 → find original in content → replaceFirst(original, targeted)
  ├─ 找到 → handleStatus=1（已接受）
  └─ 未找到 → handleStatus=3（未找到）
```

## 已知问题和待解决

1. **项目级检测未同步软删除**：`DetectionServiceImpl.submit()` 有状态机守护不会重复调用，但 `softDeleteByProjectId` 方法已预留
2. **软删除未更新审计字段**：`ver/modifyTime` 不更新，软删除后记录不再被业务查询，风险低
3. **重新检测时旧AI任务仍执行**：浪费模型Token，建议后续增加任务取消机制
4. **前端其他页面未适配targeted**：项目级 `PhaseDetection.vue` 暂未使用 `targeted` 字段

## 备注

- `targeted` 字段语义经过一次纠正：初始理解为"精确高亮定位文本"，实际应为"替换原文的内容"（替代原 suggestion 的替换角色）
- 后端软删除用原生SQL而非MyBatis-Plus的 `@TableLogic` 自动处理，与项目已有先例（`ProjectTemplateMapper.physicalDeleteByProjectId`）一致
- `handleStatus=3` 的设计使前端无需特殊处理"未找到"场景的按钮交互——该状态与1/2同属已处理，自动隐藏接受/拒绝按钮
