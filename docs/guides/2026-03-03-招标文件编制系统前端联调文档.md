## 1. 文档说明

- 文档日期：2026-03-04
- 文档范围：`ele-tender-system/ele-tender-tender-document`
- 目标读者：招标文件编制系统前端开发、联调测试人员
- 认证方式：所有接口都需要请求头 `Authorization: Bearer {externalToken}`

## 2. 统一返回格式

所有接口统一返回 `Result<T>`：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {},
  "timestamp": 1700000000000
}
```

联调约束：
- 前端统一按 `code` 判断业务结果。
- `code = 200` 表示成功。
- `code != 200` 表示业务失败。
- 业务失败时优先展示 `message`。
- `data` 尽量始终按对象处理，不依赖裸数组或裸字符串。

## 3. 异常处理约定

当前项目的统一异常处理规则如下：

- `BusinessException`：
  - HTTP 状态码一般为 `200`
  - 业务失败通过 `Result.code` 返回
- 参数校验失败：
  - `code = 400`
- 未兜底系统异常：
  - HTTP 状态码可能为 `500`
  - 返回 message 一般为“系统异常，请稍后重试”

因此：
- 联调时不要只看浏览器网络面板中的 HTTP 状态码。
- 要同时看响应体中的 `code`、`message`。

## 4. 核心业务约束

### 4.1 编制粒度

- 公开类项目：按项目级编制。
- 邀请类项目：按标段级编制。
- 前端不需要自己判断编制粒度。
- 前端在进入后只依赖 `tenderDocumentId` 继续调用后续接口。

### 4.2 项目锁

- 同一个 `projectId` 只能由首创人查看和编辑。
- 锁定维度：
  - `appKey`
  - `enterpriseCode`
  - `userId`
- 若当前用户不是首创人，后端会直接返回业务失败。

### 4.3 固定步骤

当前步骤固定为：

1. `BASIC_INFO`
2. `PURCHASE_FILE`
3. `BID_RECORD`
4. `EVALUATION_RULE`
5. `CHECK_ITEMS`
6. `GENERATE_PACKAGE`

### 4.4 页面模式

- `status = DRAFT`：编辑模式
- `status = GENERATING`：生成中，前端应禁用重复点击
- `status = COMPLETED`：查看模式

## 5. 联调总流程

### 5.1 进入编制系统

1. 业务系统先获取电子标外部 token
2. 前端进入招标文件编制页面
3. 调用 `POST /api/tender-documents/entry`
4. 从返回中拿到 `tenderDocumentId`
5. 调用 `GET /api/tender-documents/overview?tenderDocumentId={tenderDocumentId}`
6. 再按当前页面调用对应页面接口

### 5.2 页面操作

- 页面展示：调用页面查询接口
- 同步按钮：调用对应 `sync` 接口
- 文件上传：先调文件系统上传，再调编制系统 `bind`
- 采购文件步骤：需要分别绑定源采购文件和签章文件，二者齐备后才能完成并进入下一步
- 完成并进入下一步：调用统一推进接口
- 最后一步生成：调用生成接口
- 最后一步回传：调用统一回传接口

## 6. 文件联调方式

### 6.1 文件服务

文件先通过文件服务上传、查询、下载：

- `POST /file-api/upload`
- `GET /file-api/info/{fileId}`
- `GET /file-api/download/{fileId}`
- `DELETE /file-api/delete/{fileId}`

上传时必须带：
- `file`
- `bizType`

### 6.2 编制系统文件绑定

前端上传成功后，再把文件信息绑定到编制系统。

前端只需要把这些元信息传给编制系统：
- `fileId`
- `fileName`
- `fileSize`
- `contentType`
- `fileSha256`

说明：
- 编制系统不接收文件流。
- 编制系统只维护“当前项目/标段与文件的绑定关系”。
- 删除采购文件或签章文件时，本质是解绑，不删除文件系统原文件。

## 7. 接口清单

## 7.1 入口接口

### `POST /api/tender-documents/entry`

用途：
- 进入编制系统
- 命中已有草稿或创建新的编制单

请求体：

```json
{
  "bizType": 1,
  "bizId": "BIZ-001",
  "projectId": "P-001",
  "tenderId": "T-001"
}
```

返回 `data`：

```json
{
  "tenderDocumentId": 100,
  "projectId": "P-001",
  "tenderId": "T-001",
  "status": "DRAFT",
  "currentStepCode": "BASIC_INFO",
  "versionNo": 1
}
```

说明：
- 后端内部会先调用统一的基本信息同步能力。
- 若同步失败，直接返回失败，不创建编制单。

## 7.2 概览接口

### `GET /api/tender-documents/overview?tenderDocumentId={tenderDocumentId}`

用途：
- 获取页面全局壳数据
- 获取当前步骤、步骤状态、是否可编辑、版本号

返回 `data`：

```json
{
  "tenderDocumentId": 100,
  "status": "DRAFT",
  "currentStepCode": "BASIC_INFO",
  "versionNo": 1,
  "editable": true,
  "active": true,
  "stepList": [
    {
      "stepCode": "BASIC_INFO",
      "stepName": "基本信息录入",
      "stepOrder": 1,
      "stepStatus": "IN_PROGRESS",
      "active": true
    }
  ]
}
```

## 7.2.1 重新编制接口

### `POST /api/tender-documents/recompile?tenderDocumentId={tenderDocumentId}`

用途：
- 在编制单已完成（`COMPLETED`）后发起重新编制
- 将当前编制单重置为可再次生成的草稿状态

返回 `data`（与 `entry` 一致）：

```json
{
  "tenderDocumentId": 100,
  "projectId": "P-001",
  "tenderId": "T-001",
  "status": "DRAFT",
  "currentStepCode": "GENERATE_PACKAGE",
  "versionNo": 2
}
```

说明：
- 仅 `COMPLETED` 状态允许调用。
- 非 `COMPLETED` 状态调用会返回业务错误 `6021`（`当前编制单状态不允许重新编制`）。
- 重新编制后，前端可直接继续走生成流程。

## 7.6 评审规则设置

### `GET /api/tender-documents/evaluation-rules?tenderDocumentId={tenderDocumentId}`

用途：
- 加载评审规则页的概览信息
- 返回当前评标办法、标段列表和可切换分类
- 页面初始化时，分值模式请额外调用项目级 `score-type` 接口获取或回填

返回 `data`：

```json
{
  "evalMethod": "COMPREHENSIVE_SCORE",
  "tenderList": [
    {
      "tenderId": "T-001",
      "tenderName": "一标段"
    }
  ],
  "nodeCategoryList": [
    "QUALIFICATION",
    "CONFORMITY",
    "CREDIT",
    "TECHNICAL",
    "BUSINESS"
  ]
}
```

### `GET /api/tender-documents/evaluation-rules/item?tenderDocumentId={tenderDocumentId}&tenderId=T-001&nodeCategory=TECHNICAL`

用途：
- 查询某个标段、某个评审分类的规则树
- 若当前分类尚未保存，后端返回固定 `reviewMode` + 空 `treeToPageData`，不再返回“评审规则不存在”
- 分数类分类返回的 `scoreType` 来自编制单级统一配置，不属于当前标段独立保存字段
- 全通过制评标办法下，`scoreType` 允许为 `null`

返回 `data`：

```json
{
  "tenderId": "T-001",
  "tenderName": "一标段",
  "nodeCategory": "TECHNICAL",
  "reviewMode": "SCORE",
  "scoreType": "ACTUAL",
  "totalScore": 60,
  "weightRate": 100,
  "treeToPageData": []
}
```

### `PUT /api/tender-documents/evaluation-rules/item?tenderDocumentId={tenderDocumentId}&tenderId=T-001&nodeCategory=TECHNICAL`

用途：
- 保存某个标段、某个评审分类的规则树
- `reviewMode` 由后端按 `evalMethod + nodeCategory` 固定推导，前端无需传
- `QUALIFICATION`、`CONFORMITY`、`DETAIL` 固定为 `PASS`
- `CREDIT`、`TECHNICAL`、`BUSINESS` 固定为 `SCORE`
- 该接口不再保存 `scoreType`
- 分数类分类只保存当前标段自己的节点树、`totalScore`、`weightRate`

请求体示例：

```json
{
  "totalScore": 60,
  "weightRate": 100,
  "treeToPageData": [
    {
      "id": "9d3ec5d3-24d4-4ef5-abeb-d72dfe2c3b3c",
      "order": 1,
      "key": "1",
      "name": "技术方案完整性",
      "isPass": false,
      "lowest": 0,
      "highest": 10,
      "standard": "按方案完整性评分",
      "isParent": true,
      "objectiveType": "SUBJECTIVE",
      "children": []
    }
  ]
}
```

### `GET /api/tender-documents/evaluation-rules/score-type?tenderDocumentId={tenderDocumentId}`

用途：
- 查询当前编制单统一使用的 `scoreType`
- 适用于页面初始化、切换评审分类后回填分值模式

返回 `data`：

```json
{
  "scoreType": "ACTUAL"
}
```

说明：
- `LOWEST_PRICE` 等全通过制评标办法下，返回值允许为 `null`

### `PUT /api/tender-documents/evaluation-rules/score-type?tenderDocumentId={tenderDocumentId}`

用途：
- 修改当前编制单统一使用的 `scoreType`
- 会影响当前编制单下所有标段的分数类分类展示与跨分类校验

请求体示例：

```json
{
  "scoreType": "WEIGHT"
}
```

清空示例（仅全通过制场景或草稿态允许）：

```json
{
  "scoreType": null
}
```

### `POST /api/tender-documents/evaluation-rules/copy?tenderDocumentId={tenderDocumentId}`

用途：
- 将来源标段评审规则整体复制到目标标段
- 仅复制目标标段自己的规则头和节点树，不修改项目级 `scoreType`

请求体：

```json
{
  "sourceTenderId": "T-001",
  "targetTenderId": "T-002"
}
```

## 8. 联调注意事项

- `entry` 成功后，前端只保存 `tenderDocumentId` 即可。
- 不要让前端自行判断 `compileScope`。
- `basic-info/sync` 是唯一的项目信息同步入口。
- `purchase-file` 及其签章文件接口都不直接上传文件流到编制系统。
- `evaluation-rules` 页面以树结构收发，前端负责渲染层级编号。
- `generate/callback` 对前端只有一个按钮，对后端内部仍是两类文件分别回传。
- 统一回传接口在“部分失败”场景也可能返回 `code = 200`，前端必须按 `data.success` 决定提示与重试引导。
