# 方案计划（2026-03-20）- 回传接口偶发死锁治理候选

## 目标
- 消除或显著降低 `td_tender_document_callback` 在并发回传下的死锁概率
- 保持“回传次数（retryCount）递增可追溯”能力
- 不引入“重复回传外部业务系统”副作用

## 方案 A（最小改动，快速止血）
### 思路
- 保留现有表与逻辑。
- 将“回传网关调用”与“回传记录入库”解耦：
  - 网关调用仍执行一次；
  - 对数据库留痕（`select for update + insert`）做有限重试（仅重试数据库写入段，不重试网关调用）。
- 同时补充联合索引，降低锁冲突概率。

### 变更点
1. `callbackFile` 内将 DB 留痕段封装为独立方法（事务短、可重试）。
2. 捕获 `DeadlockLoserDataAccessException` / `MySQLTransactionRollbackException`，指数退避重试 2~3 次。
3. 新增索引（建议）：
   - `idx_doc_callback_retry`(`tender_document_id`,`version_no`,`file_role`,`tender_id`,`retry_count`,`id`)

### 优点
- 改动小，见效快。
- 对现有业务模型影响最小。

### 风险
- 治标为主；高并发极端场景仍可能发生重试失败。
- 需要确认线上数据量下索引变更窗口。

## 方案 B（推荐，中期稳态）
### 思路
- 去掉“在历史明细表上 `for update` 取最大重试次数”模式。
- 新增“计数器表”按 `(tender_document_id, version_no, file_role, tender_id)` 维护当前重试计数，使用原子 upsert 递增。
- 回传明细表仅做 append，不参与计数竞争锁。

### 变更点
1. 新建表（示例）：`td_tender_document_callback_counter`
   - 唯一键：`(tender_document_id, version_no, file_role, tender_id)`
   - 字段：`current_retry_count`
2. 使用原子 SQL 获取下一次重试号：
   - `insert ... on duplicate key update current_retry_count = current_retry_count + 1`
3. 将获取到的 `current_retry_count` 写入 `td_tender_document_callback.retry_count`。

### 优点
- 从根上减少死锁触发面。
- 明细写入与计数竞争解耦，可扩展性更好。

### 风险
- 需要一次 DDL + DAO 改造 + 回归测试。
- 需要明确 `tender_id null` 在唯一键中的处理策略（建议统一归一化占位值）。

## 方案 C（并发入口限流/互斥）
### 思路
- 在应用层对同一 `tenderDocumentId`（或更细粒度 key）做短时互斥（如 Redis `SETNX`）。
- 同一编制单并发回传请求直接返回“处理中，请稍后重试”。

### 优点
- 实现简单，能快速减少并发竞争。

### 风险
- 只降低并发，不解决底层 SQL 竞争设计问题。
- 需处理锁过期和异常释放。

## 推荐顺序
1. 先落地方案 A：短期止血（低风险、可快速上线）
2. 再推进方案 B：中期根治（结构化治理）
3. 方案 C 作为补充防抖，不建议单独作为最终方案

## 验证计划（实施后）
1. 并发压测同一 `tenderDocumentId` 下 20~50 并发调用 `/generate/callback`。
2. 核验：
   - 无死锁错误；
   - `retry_count` 连续递增；
   - 无重复外部回传（同一次请求只发一次网关调用）。
3. 观察窗口：
   - 生产 `sup_access_log` + 应用异常日志 24h。
