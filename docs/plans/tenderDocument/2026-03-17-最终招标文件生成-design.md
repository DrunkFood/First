# 最终招标文件生成 Design

## 背景

当前招标文件编制系统已经具备生成页、生成动作与回传动作的流程壳子，但 `generatePackage` 仍停留在一期临时实现：

- 默认实现只伪造产物文件
- 交互实现主要把源采购文件与签章 PDF 打成 zip
- 生成页与回传模型仍围绕“数据包列表 + 编制回执 + 多文件角色回传”组织

这与当前目标不一致。当前目标是由招标文件编制系统后端直接生成正式的最终招标文件数据包，并将其作为正式封版结果保存、展示与回传。

## 设计目标

- 点击“生成采购文件数据包”后，由后端一次性生成正式数据包
- 数据包明文基于当前编制单最新数据实时组装
- 明文 JSON 内嵌签章后的招标文件 PDF 内容
- 在招标文件编制系统内完成加密
- 加密后的正式数据包通过文件服务保存
- 同时生成一份“采购文件编制信息”PDF，供用户下载
- 生成完成后编制单进入完成态，不允许再次编辑和再次生成
- 回传时回传签章 PDF 与最终数据包，不回传“采购文件编制信息”
- 生成与回传全流程保留可查询的业务留痕

## 方案对比

### 方案一：最小替换 `generatePackage`

- 做法：
  - 保留现有服务结构
  - 仅把 zip 构建逻辑替换成“JSON 组装 + 加密”
  - 再补一个“采购文件编制信息”PDF 生成
- 优点：
  - 改动面最小
- 缺点：
  - 多包生成、旧回传语义仍会残留
  - 后续不同业务系统后缀/加密器扩展会继续受旧模型限制

### 方案二：同步生成编排器

- 做法：
  - 对外仍保留单个生成按钮和同步接口
  - 对内拆成数据采集、签章 PDF 加载、JSON 组装、加密、正式包保存、`采购文件编制信息` 生成、状态更新等职责清晰的组件
- 优点：
  - 业务语义清晰
  - 可自然承接 `GENERATING` 状态、单包模型、日志留痕与可插拔扩展
- 缺点：
  - 改动比方案一大

### 方案三：异步生成任务

- 做法：
  - 点击按钮后仅创建任务
  - 后台异步完成数据包和 PDF 生成
- 优点：
  - 适合很重的模板与复杂加密
- 缺点：
  - 当前需求没有必要引入任务、轮询、恢复等额外复杂度

## 选型

采用方案二。

对外保持“单次点击、同步生成”的体验，对内重构为清晰的生成编排流程，为后续不同业务系统后缀、不同加密实现与格式升级预留扩展点。

## 核心业务模型

### 1. 编制单状态

`TenderDocument.status` 维持现有三态，但需要真正用起来：

- `DRAFT`：编制中
- `GENERATING`：生成中
- `COMPLETED`：已生成完成

状态流转规则：

- 成功：`DRAFT -> GENERATING -> COMPLETED`
- 失败：`DRAFT -> GENERATING -> DRAFT`
- `GENERATING` 禁止重复点击
- `COMPLETED` 禁止再次生成

### 2. 产物模型

一个编制单最终只生成两份正式产物：

- `FINAL_PACKAGE_FILE`
  - 正式最终招标文件数据包
  - 唯一正式回传主文件
- `COMPILE_INFO_PDF`
  - “采购文件编制信息”
  - 仅供下载/打印，不回传

另保留生成输入与回传文件：

- `SIGNED_PDF`
  - 作为最终 JSON 嵌入源
  - 回传业务系统

所有文件二进制统一通过文件服务保存，编制模块只记录 `TenderDocumentFile` 关联关系。

### 3. 生成粒度

- 一个编制单只生成一份总包
- 项目级编制单：总包包含项目下所有标段数据
- 标段级编制单：总包仅包含当前标段数据

因此，旧的“邀请类项目按标段逐个生成多个数据包”的实现需要废弃。

### 4. 文件命名规则

- 点击“生成文件”时，文件命名规则固定如下：
  - PDF 文件：`[上传的文件名不变][yyyyMMddHHmmss].pdf`
  - 最终数据包文件：`[项目编号]采购文件电子数据包[yyyyMMddHHmmss].HzctZbs`
- 时间戳精度到秒，格式统一为 `yyyyMMddHHmmss`
- 当前后缀按 `.HzctZbs` 输出，后续接入不同业务系统可替换后缀，但命名主体保持一致

## 系统组件设计

建议在 `ele-tender-tender-document` 模块内收敛出以下职责：

- `FinalPackageDataAssembler`
  - 读取当前编制单最新业务数据
  - 组装最终 JSON 明文对象
- `SignedPdfContentLoader`
  - 从文件服务读取 `SIGNED_PDF`
  - 输出 Base64 与元信息
- `FinalPackageEncryptor`
  - 将 JSON 明文字节加密为最终二进制结果
  - 后续可按业务系统切换实现
- `FinalPackageFileWriter`
  - 将加密后的最终数据包写入文件服务
  - 文件后缀通过配置决定，当前默认可为 `.HzctZbs`
- `CompileInfoPdfGenerator`
  - 生成带水印的“采购文件编制信息”PDF
- `GenerationPersistenceManager`
  - 统一负责文件关联、状态更新、完成时间落库与记录入库
- `GenerationRecordService`
  - 管理生成记录主表与查询

## `POST /generate` 时序

### 步骤 1：读取并锁定编制单

- 校验当前用户是否仍持有项目锁
- 查询当前编制单
- 仅允许 `DRAFT` 状态进入生成流程

### 步骤 2：抢占生成状态

- 使用条件更新将状态从 `DRAFT` 原子改为 `GENERATING`
- 若更新失败：
  - 当前状态为 `GENERATING`：返回“当前正在生成，请勿重复提交”
  - 当前状态为 `COMPLETED`：返回“当前编制单已生成完成，不允许再次生成”

### 步骤 3：生成前置校验

至少校验：

- 前置步骤已完成
- 存在有效 `SIGNED_PDF`
- 当前编制单存在组装最终包所需的业务数据
- 当前不存在有效的 `FINAL_PACKAGE_FILE`
- 当前不存在有效的 `COMPILE_INFO_PDF`

### 步骤 4：采集最新业务数据

- 直接读取当前编制单相关业务表
- 不基于历史版本快照
- 项目级编制单采集全部标段数据
- 标段级编制单采集当前标段数据

### 步骤 5：读取签章 PDF

- 通过文件服务下载 `SIGNED_PDF`
- 获取文件名、大小、SHA-256 与文件内容
- 将文件内容转为 Base64 字符串

### 步骤 6：组装最终 JSON 明文

由 assembler 输出固定结构：

- `baseInfo`
- `tenders`
- `tenderDocumentSignPdf`
- `caKeysInfo`
- `settings`
- `versionInfo`

其中：

- `bidEvalRules` 分类 key 固定为：
  - `QUALIFICATION`
  - `CONFORMITY`
  - `DETAIL`
  - `CREDIT`
  - `TECHNICAL`
  - `BUSINESS`
- `QUALIFICATION`、`CONFORMITY`、`DETAIL` 使用同类结构
- 规则字段名统一为 `objectiveType`
- `tenderDocumentUniqueCode` 在生成时由系统生成纯系统码

### 步骤 7：执行加密

- 将 JSON 明文字节整体送入 `FinalPackageEncryptor`
- 输出加密后二进制
- 文件后缀从配置读取，不在业务代码中写死

### 步骤 8：保存最终数据包

- 将加密后二进制上传到文件服务
- 文件名按规则生成：`[项目编号]采购文件电子数据包[yyyyMMddHHmmss].HzctZbs`
- 记录为 `FINAL_PACKAGE_FILE`

### 步骤 9：生成“采购文件编制信息”PDF

- 基于本次生成上下文生成 PDF
- 加水印
- 文件名按规则生成：`[上传的文件名不变][yyyyMMddHHmmss].pdf`
- 保存到文件服务，记录为 `COMPILE_INFO_PDF`

### 步骤 10：落库并封版

在数据库事务中执行：

- 旧的同角色有效文件置无效
- 插入新的 `FINAL_PACKAGE_FILE`
- 插入新的 `COMPILE_INFO_PDF`
- 记录完成时间
- 标记生成步骤完成
- 更新 `TenderDocument.status = COMPLETED`
- 保持 `currentStepCode = GENERATE_PACKAGE`
- 插入完成版本记录
- 更新生成记录为成功

### 步骤 11：失败回滚与状态恢复

若在组装、加密、文件服务写入、PDF 生成、数据库落库任一环节失败：

- 记录失败日志与失败生成记录
- 将 `TenderDocument.status` 从 `GENERATING` 回退到 `DRAFT`
- 不对前端暴露半成品状态

注意：

- 文件服务中可能产生孤儿文件，需要在后续实施中补充清理策略
- 但主业务状态必须保持一致

## `POST /generate/callback` 设计

### 目标

- 回传动作只负责将已生成/已绑定文件回传给业务系统
- 与生成动作完全解耦

### 回传范围

顺序固定为：

1. 回传 `SIGNED_PDF`
2. 回传 `FINAL_PACKAGE_FILE`

不回传 `COMPILE_INFO_PDF`。

### 回传记录

- 按文件角色分别留痕
- 同一版本、同一文件角色保留多次回传记录
- 页面只展示签章 PDF 与最终数据包的回传历史

## 页面与接口返回模型

生成页建议收敛为单产物模型，避免继续沿用“多包列表”语义。

建议返回：

- `status`
- `versionNo`
- `compileCompleteTime`
- `signedFile`
- `finalPackageFile`
- `compileInfoFile`
- `callbackHistory`
- `latestGenerateRecord`
- `generating`

说明：

- `signedFile` 对应 `SIGNED_PDF`
- `finalPackageFile` 对应 `FINAL_PACKAGE_FILE`
- `compileInfoFile` 对应 `COMPILE_INFO_PDF`
- `callbackHistory` 仅包含签章 PDF 与最终数据包的回传记录

## 生成记录与日志

### 1. 系统级日志

沿用现有 `traceId` 与控制台结构化日志，关键节点打印：

- 开始生成
- 抢占状态成功/失败
- 校验通过/失败
- 读取签章 PDF
- 组装 JSON
- 执行加密
- 保存最终数据包
- 生成“采购文件编制信息”
- 状态更新完成
- 失败结束

### 2. 业务级生成记录

建议新增生成记录表，至少记录：

- `tender_document_id`
- `version_no`
- `project_id`
- `tender_id`
- `trace_id`
- `generate_status`
  - `PROCESSING`
  - `SUCCESS`
  - `FAIL`
- `start_time`
- `finish_time`
- `duration_ms`
- `operator_id`
- `operator_name`
- `signed_file_id`
- `signed_file_name`
- `final_package_file_id`
- `final_package_file_name`
- `compile_info_file_id`
- `compile_info_file_name`
- `package_sha256`
- `file_suffix`
- `error_code`
- `error_message`
- `detail_json`

要求：

- 生成开始先落一条 `PROCESSING`
- 成功或失败都更新终态
- 生成记录写入不应因主事务回滚而完全丢失

## 异常处理

建议明确业务错误场景：

- 正在生成中重复点击
- 已生成完成再次点击
- 缺少签章 PDF
- 缺少最终 JSON 组装必要数据
- 文件服务上传失败
- 加密失败
- PDF 生成失败

对前端返回统一 `Result` 结构，对内部记录完整错误消息。

## 测试设计

至少覆盖：

- `GENERATING` 状态下重复点击被拦截
- `COMPLETED` 状态下重复点击被拦截
- 生成失败时状态回退到 `DRAFT`
- 项目级编制单只生成一份总包，且包含全部标段数据
- 标段级编制单只生成一份总包，且仅包含当前标段数据
- 最终 JSON 结构符合约定
- `tenderDocumentUniqueCode` 正确生成
- `SIGNED_PDF` 正确嵌入 JSON
- 只生成一份 `FINAL_PACKAGE_FILE` 和一份 `COMPILE_INFO_PDF`
- 回传只覆盖 `SIGNED_PDF` 与 `FINAL_PACKAGE_FILE`
- 生成记录成功/失败均写入
