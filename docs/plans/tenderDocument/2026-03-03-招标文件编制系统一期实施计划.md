# 招标文件编制系统一期实施计划

> 备注：本文件为历史实施计划。当前招标文件编制系统已按后续实现与文档演进落地，尤其签章环节已并入采购文件上传环节，不再保留独立 `ELECTRONIC_SIGN` 步骤。查阅当前实现时，以 `ele-tender-system/ele-tender-tender-document/README.md`、`docs/projects/2026-03-04-招标文件编制系统接口文档-openapi3.yaml` 及最新代码为准。

## 1. 计划说明

- 文档日期：2026-03-04
- 适用范围：`ele-tender-system/ele-tender-tender-document`
- 目标：将当前已实现但与最新业务确认存在偏差的招标文件编制模块，调整为“页面导向接口 + 公开类项目级 / 邀请类标段级编制”的正式版本。

## 2. 当前问题

当前分支中 `ele-tender-tender-document` 已具备较完整的后端骨架，但存在以下偏差：

- 对前端暴露的接口更偏后端内部模型，不够页面化。
- 历史设计默认编制单偏项目级，未完全体现“公开类项目级 / 邀请类标段级”的编制粒度。
- 前端联调需要的是直接可渲染的数据结构，而不是快照字符串和步骤通用模型。
- 统一返回格式虽然沿用全局 `Result<T>`，但招标文件编制模块尚未形成受控异常码规范。
- 前端页面“统一回传”按钮与后端“分两类文件回传”的边界尚未在接口和实现中统一。

## 3. 一期调整目标

本轮实施只做以下事情：

1. 将入口规则调整为复用统一基本信息同步能力。
2. 将对前端的接口收敛为页面接口。
3. 将编制单归属改为：
   - 公开类：项目级
   - 邀请类：标段级
4. 固化统一返回格式、异常码规范、URL 规范。
5. 同步更新设计文档、前端联调文档、Swagger 2.0 文档和 `AGENTS.md`。
6. 在不影响其他分支和本 worktree 无关脏改动的前提下完成最小必要代码改造与测试。

## 4. 不做范围

本轮不做：

- 检查项自动校验引擎
- 最终数据包格式细化
- 自动重试调度
- 前端页面实现
- 与业务系统的真实联调打通
- 对无关模块脏改动的清理、整理或合并

## 5. 实施顺序

## 阶段一：文档与规范先行

### 任务 1：重写正式设计文档

目标：
- 固化最新业务规则和页面接口设计。

完成标准：
- 设计文档中明确：
  - 统一返回格式
  - 当前全局异常处理行为
  - TenderDocument 异常码区间
  - 编制粒度
  - 入口规则
  - 页面接口清单
  - URL 规范

### 任务 2：重写前端联调文档

目标：
- 让前端只看一份页面化接口文档即可联调。

完成标准：
- 清楚写明：
  - `entry -> overview -> 页面接口` 调用顺序
  - 文件上传与绑定方式
  - 统一回传按钮对应的后端行为
  - 所有页面接口请求和返回示例

### 任务 3：重写实施计划文档

目标：
- 让后续代码调整严格按新设计执行。

完成标准：
- 计划中不再沿用旧的项目级固定编制单假设。
- 计划中先改入口与页面协议，再改内部模型和控制器。

## 阶段二：入口与核心归属模型调整

### 任务 4：调整编制单主模型

改动目标：
- 在 `TenderDocument` 主表和实体中显式体现 `compileScope`。
- 公开类允许项目级编制单。
- 邀请类允许标段级编制单。

完成标准：
- `td_tender_document` 支持：
  - `compile_scope`
  - `project_id`
  - `tender_id`
- 命中规则调整为：
  - `PROJECT`：`bizType + bizId + projectId`
  - `TENDER`：`bizType + bizId + projectId + tenderId`

### 任务 5：重写 `entry`

改动目标：
- `entry` 只接收最小请求参数：
  - `bizType`
  - `bizId`
  - `projectId`
  - `tenderId`
- `entry` 内部直接调用统一的基本信息同步能力。

完成标准：
- `entry` 若同步失败则直接返回失败，不创建编制单。
- `entry` 响应只返回：
  - `tenderDocumentId`
  - `projectId`
  - `tenderId`
  - `status`
  - `currentStepCode`
  - `versionNo`

## 阶段三：对前端暴露的接口改为页面模型

### 任务 6：重写概览接口

目标：
- 提供单独的页面壳接口。

接口：
- `GET /api/tender-documents/overview/{tenderDocumentId}`

完成标准：
- 返回：
  - `tenderDocumentId`
  - `status`
  - `currentStepCode`
  - `versionNo`
  - `editable`
  - `active`
  - `stepList`

### 任务 7：重写前三个页面接口

范围：
- 基本信息录入
- 采购文件编制
- 开标标录设置

完成标准：
- 不再向前端返回 `snapshotJson` 字符串。
- 返回结构可直接渲染。
- 文件页只返回文件元信息，不返回下载 URL。

### 任务 8：重写后四个页面接口与统一推进接口

范围：
- 评审规则设置
- 检查项
- 电子签章
- 生成文件
- `complete-and-next`

完成标准：
- 评审规则页按：
  - 页面概览接口
  - `tenderId + nodeCategory` 节点接口
  - 复制接口
- 生成页仅提供一个统一回传接口：
  - `POST /api/tender-documents/generate/callback/{tenderDocumentId}`
- 后端统一回传接口内部再拆成：
  - 签章文件回传
  - 数据包回传

## 阶段四：内部服务适配

## 6. 风险与控制

### 风险 1：当前 worktree 存在大量无关脏改动

处理：
- 只修改招标文件编制相关文件。
- 不触碰前端及其他模块的既有脏改动。
- 提交时仅暂存本次相关文件。

### 风险 2：旧 controller 与新 controller 同时存在导致契约混乱

处理：
- 明确以新页面接口为准。
- 文档、Swagger、controller 同步收敛。

### 风险 3：异常码文档和实现再次脱节

处理：
- 先更新规范文档，再改代码。
- 新增异常码必须回写文档。
