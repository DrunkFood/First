# ele-tender-crypto 模块开发计划

> 创建时间：2026-03-30
> 规范文档：`docs/projects/ELE_TENDER_CRYPTO_SPEC.md`

## Context

本次开发属于电子标系统 **2.0.0 大版本迭代**。目标是在现有仓库内新增 `ele-tender-crypto` 模块，并同步完成 external token 多会话兼容改造、interaction starter 扩展和 support 管理能力补充。

本次范围内的核心原则：

- `ele-tender-crypto` 只保留 external-facing 接口
- 管理查询、人工重试、访问日志查询统一收口到 `ele-tender-support`
- 解密模型拆分为 `artifact` 和 `request`
- 不在 MySQL 中存储原始 `bidderPwdStr`
- 2.0.0 版本号统一作为独立发布准备阶段处理，不阻塞功能开发主链路

## Phase 2: external token 多会话兼容改造

### 目标

解决同一外部用户在多个业务入口、多个页面或多个服务实例并发操作时 external token 相互顶掉的问题，并保持用户与业务系统无感知。

### 修改范围

| 模块 | 文件/方向 | 改动 |
|------|-----------|------|
| `ele-tender-common` | `JwtAuthenticationFilter` | external token 校验支持 `jti` |
| `ele-tender-common` | `LoginUser` | 可选新增 external session 上下文字段 |
| `ele-tender-support` | `AuthServiceImpl` | 签发 external token 时自动生成 `jti`，Redis 改为多会话 key |
| `ele-tender-support` | 相关测试 | 增加新旧 token 兼容测试 |
| `ele-tender-tender-document` | JWT 鉴权回归 | 验证能识别新 token |
| `ele-tender-crypto` | 后续新模块 | 直接使用新 external token 规则 |

### 设计要求

- 新 external token 自动带 `jti`
- Redis key 改为 `external:token:{appKey}:{userId}:{jti}`
- 校验时兼容无 `jti` 的旧 token
- internal token 逻辑保持不变
- 对调用方返回结构保持不变，业务系统无需感知 `jti`

### 验证

```bash
cd ele-tender-system
mvn -pl ele-tender-common -am clean test
mvn -pl ele-tender-support -am clean test
mvn -pl ele-tender-tender-document -am clean test
```

### 6.4 JNI 接口层

| 文件 | 说明 |
|------|------|
| `ICryptoNative.java` | 字节契约：`unpackFile()`、`packFile()`、`encryptSegments()`、`decryptSegments()`、`rsaEncrypt()`、`rsaDecrypt()`、`sha256()` |
| `UnpackResult.java` | unpack 返回值，使用 `List<byte[]>` / `byte[]` 承载分段密文与 RSA 密文 |
| `StubCryptoNative.java` | Java stub，用于联调与测试 |
| `JniCryptoNative.java` | C++ ready 后接入真实 JNI |

| 文件 | 说明 |

### 6.6 Service

| 接口 | 实现 | 职责 |
|------|------|------|
| `IBidDocumentService` | `BidDocumentServiceImpl` | 文件预存：下载、散列存储、写 `bdc_bid_document`、回调 |
| `IBidDecryptRequestService` | `BidDecryptRequestServiceImpl` | 提交解密请求、创建 request、关联 artifact、投递 stream |
| `IDecryptArtifactService` | `DecryptArtifactServiceImpl` | artifact 去重、状态迁移、解密结果复用 |
| `IDecryptExecutor` | `DecryptExecutorImpl` | unpack、RSA、校验、解密、JSON 解析、更新 artifact |
| `ICallbackService` | `CallbackServiceImpl` | 按 request 回调业务系统 |

### 6.7 Consumer / Scheduler

| 文件 | 说明 |
|------|------|
| `DecryptTaskStreamConsumer.java` | 消费 `artifactId`，触发 artifact 执行 |
| `DecryptTimeoutRecoveryScheduler.java` | 扫描超时 artifact，控制重试或失败终态 |

### 6.8 Controller

只保留：

| Controller | 端点 | 认证 |
|-----------|------|------|
| `BidDocumentController` | `POST /api/crypto/bid-document/push` | External JWT |
| `BidDecryptController` | `POST /api/crypto/bid-decrypt/submit`、`GET /api/crypto/bid-decrypt/status/{recordId}` | External JWT |

### 6.9 数据库初始化脚本

建表：

- `bdc_bid_document`
- `bdc_decrypt_artifact`
- `bdc_decrypt_request`

关键约束：

- `uk_artifact_lookup (app_key, file_sha256, bidder_pwd_fingerprint)`

- `idx_request_bid_record (app_key, bid_record_id)`

- 不加数据库外键

## 端到端验证

1. 编译：`cd ele-tender-system && mvn clean compile`
2. token 多会话验证：
   - 同一 `appKey + userId` 连续获取两个 external token
   - 验证两个 token 在兼容窗口内都可通过目标业务接口
3. 文件预存测试：
   - 获取 external token
   - `POST /api/crypto/bid-document/push`
   - 检查文件散列存储路径
   - 检查回调到达业务系统 stub
4. 解密测试：
   - `POST /api/crypto/bid-decrypt/submit` 返回 `recordId`
   - 检查 request 创建、artifact 命中或创建、stream 消息投递
   - 检查 consumer 消费和 artifact 状态变化
   - 检查 request 回调到达业务系统 stub
5. 去重测试：
   - 相同 `(app_key, file_sha256, bidder_pwd_fingerprint)` 再次提交
   - 验证不重复解密，仅新增 request 并复用 artifact
6. 超时恢复测试：
   - 模拟 artifact PROCESSING 超时
   - 验证 scheduler 重置或标记失败
7. support 管理能力测试：
   - internal token 访问 support 的 crypto 管理接口
   - `/api/access-logs` 按 `serviceName=ele-tender-crypto` 查询日志
