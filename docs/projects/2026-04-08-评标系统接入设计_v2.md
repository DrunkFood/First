# 评标系统接入设计 v2

> 日期：2026-04-08
> 状态：设计修订稿
> 适用范围：EleTender 平台一期评标能力接入
> 替代关系：本稿用于替代 `2026-04-07-评标系统接入设计.md`

## 一、修订背景

`2026-04-07-评标系统接入设计.md` 已明确“全新建设评标模块”的总体方向，但在接入边界上仍有几个关键空缺：

- 未明确 `crypto` 逐条推送后，何时才允许真正启动评标
- 未明确同步载荷的幂等键、排序键、联合体标识和失败补偿规则
- 未区分“专家前台登录凭证”和“服务间内部调用凭证”
- 未明确旧系统中的反查/下载能力是否保留、由谁替代
- “参考现有系统设计”的表述过宽，容易误导为复用旧 JSON 协议

本版设计以 **EleTender 现有技术基线、v9 招投标文件格式、现有 common/file/interaction 基础设施** 为准，对评标接入方案重新收敛。

## 二、参考依据与边界

### 2.1 已核对的参考系统

本次仅核对到以下接入侧实现：

- `originalCryptoSystem/information-biddingfile-decrypt`

该系统可提供的参考主要是：

- 解密完成后逐条向评标系统推送结构化数据
- 推送时依赖 `tenderId + netBidId` 一类上游标识
- 附件曾按本地磁盘目录方式落盘并提供下载
- 评标侧曾存在反查招标文件版本的回调接口

### 2.2 不作为本次复用对象的内容

以下内容 **不直接复用**：

- `originalCryptoSystem` 中的旧版投标文件 JSON 字段结构
- 旧系统的本地磁盘目录下载协议
- 旧系统的 JDK 8 / Spring Cloud / Nacos 技术选型

### 2.3 本次设计的明确前提

- 评标模块为 **全新建设**
- 评标接入数据以 **EleTender v9 解密产物** 为准
- “参考现有系统”仅指参考其 **流程经验、边界划分、幂等思路**，不指协议和实现复制
- 一期只支持：
  - 最低评标价法
  - 综合评分法
  - 专家评审
  - 少于三家投票

## 三、核心设计结论

| 维度 | 结论 |
|------|------|
| 后端模块 | 新建 `ele-tender-evaluation`，端口 `8084`，表前缀 `eval_` |
| 前端应用 | 新建 `ele-tender-evaluation-frontend`，端口 `3001` |
| 评标对象粒度 | **一个 `tenderId` 对应一个评标项目** |
| 接入协议来源 | 以 EleTender v9 解密结果为准，不复用旧系统字段名 |
| 数据接入模式 | `crypto` 逐条推送投标人数据，`business/evaluation` 推送专家与启动指令 |
| 启动条件 | 只有在“数据齐备且专家齐备”后，项目才能从 `INIT` 进入 `READY`/`REVIEWING` |
| 幂等主键 | 投标人同步以 `(tender_id, net_bid_id)` 为唯一键 |
| 文件策略 | 解密得到的 PDF 由 `evaluation` 解码后上传 `file` 服务，评标侧只存 `fileId` 和摘要 |
| 认证策略 | 专家前台使用 `EVALUATION` token；服务间调用继续使用 `INTERNAL` 能力 |
| 结果回传 | 通过 Interaction 机制回传业务系统，返回体使用 `InteractionResult<T>` |
| 追踪 | 全链路透传 `X-Trace-Id`，MDC 键固定 `traceId` |

## 四、总体架构

### 4.1 数据流

```text
业务系统
  ├─ 推送专家名单/项目信息 ───────────────→ evaluation :8084
  ├─ 推送启动评标指令 ──────────────────→ evaluation :8084
  └─ 接收评标结果回传 ←──── interaction / starter ← evaluation :8084

crypto :8083
  └─ 解密成功后逐条推送投标人结构化数据 ─→ evaluation :8084

evaluation :8084
  ├─ 落库项目/投标人/规则/评审结果
  ├─ 抽取附件并上传 file :8081
  ├─ 通过 WebSocket 向前端广播项目状态
  └─ 代理专家前端的文件下载请求

evaluation-frontend :3001
  └─ 仅访问 evaluation :8084
```

### 4.2 不再保留的旧链路

一期不复制旧系统中的以下能力：

- `evaluation -> crypto` 的“反查招标文件版本”接口
- `evaluation -> crypto` 的“按磁盘目录下载附件”接口

原因如下：

- `crypto` 在推送前已完成投标文件归属、版本等校验
- v9 解密结果中已包含 `versionInfo`
- 评标所需附件在同步时即可由 `evaluation` 自身归档到 `file` 服务

即：**一期设计采用“推送即归档”，不采用“评标时再回源拉取 crypto 磁盘文件”**。

## 五、认证与安全边界

### 5.1 Token 类型划分

| 场景 | 凭证类型 | 说明 |
|------|----------|------|
| 专家登录 evaluation 前端 | `EVALUATION` | 仅用于评标前台与评标后端 |
| `crypto -> evaluation` 内部推送 | `INTERNAL` | 服务间调用，不使用专家 token |
| `evaluation -> file` | `INTERNAL` | 评标后端代理文件访问 |
| `evaluation -> interaction` 或通过 starter 回调业务系统 | 内部服务能力 / 签名头 | 不透传专家 token |
| 外部业务系统用户访问 interaction | `EXTERNAL` | 维持现有 interaction 机制 |

### 5.2 安全原则

- `EVALUATION` token 只被 `ele-tender-evaluation` 接受
- `support` / `file` / `tender-document` / `crypto` 不对 `EVALUATION` token 开放业务接口
- 评标后端访问其他服务时必须使用内部服务凭证，不能拿专家 token 透传
- 所有内部同步接口默认要求登录和权限校验，并记录 `traceId`
- 所有同步接口都需要幂等，允许同一请求重放

## 六、业务对象与生命周期

### 6.1 评标项目定义

- 评标项目唯一主键使用内部自增/雪花 ID
- 业务唯一键使用 `tenderId`
- 同一个 `projectId` 下若有多个标段，则每个 `tenderId` 独立形成一个评标项目

### 6.2 项目阶段

```text
INIT
  -> WAIT_EXPERT_SYNC
  -> READY
  -> REVIEWING
  -> RESULT_CONFIRMED
  -> CALLBACK_SUCCESS
  -> FINISH
```

状态说明：

- `INIT`
  - 项目已创建
  - 正在接收投标人同步数据
- `WAIT_EXPERT_SYNC`
  - 投标人数据已满足启动前置条件
  - 但专家名单未齐备
- `READY`
  - 投标人和专家数据均齐备
  - 尚未正式进入首个评审节点
- `REVIEWING`
  - 处于资格/符合性/详细/资信/技术/商务等节点之一
- `RESULT_CONFIRMED`
  - 最终结果已确认，等待回传
- `CALLBACK_SUCCESS`
  - 结果已成功回传业务系统
- `FINISH`
  - 项目闭环结束

### 6.3 启动前置条件

项目只有同时满足以下条件才允许启动：

- 至少收到一条投标人同步数据
- `sync/start` 指令已到达
- 专家名单已同步完成或在评标模块内已确认齐备
- 同步失败的投标人是否允许忽略，已由启动指令显式声明

若未满足条件，`sync/start` 只记录“启动申请”，不直接将项目推进到 `REVIEWING`。

## 七、评审流程设计

### 7.1 评审节点

最低评标价法：

- `QUALIFICATION`
- `CONFORMITY`
- `DETAIL`
- `FINAL_RESULT`

综合评分法：

- `QUALIFICATION`
- `CONFORMITY`
- `CREDIT`
- `TECHNICAL`
- `BUSINESS`
- `FINAL_RESULT`

### 7.2 节点内状态

```text
PENDING -> EXPERT_SCORING -> EXPERT_CONFIRMED -> LEADER_REVIEW -> NODE_CONFIRMED -> COMPLETED
```

说明：

- 专家先提交个人结果，再进行个人确认
- 组长查看汇总结果后确认推进
- “偏差阈值”作为配置项保存在项目表，默认 `20%`
- 因未取得 `original-info-eval-total` 代码，本版仅保留阈值机制，不固化旧系统的全部判定细节

### 7.3 少于三家

一期保留“少于三家投票”能力，但触发口径明确为：

- **在项目正式进入首个评审节点前**
- 按“已成功同步并进入评标名单的投标人数”判断
- 若数量 `< 3`，触发投票

投票选项：

- 继续评标
- 废标
- 重新招标

一期不在后续节点中重复触发该投票。

## 八、同步协议设计

### 8.1 统一约束

- 内部同步接口前缀统一为 `/api/eval/internal/*`
- 返回结构统一为 `Result.success(data)` / `Result.fail(code, msg)`
- 所有请求要求透传 `X-Trace-Id`
- 所有写接口必须幂等

### 8.2 投标人同步

`POST /api/eval/internal/sync/bidder`

用途：

- `crypto` 在某个投标文件解密并校验成功后，向 `evaluation` 推送一条投标人结构化数据

建议请求体：

```json
{
  "tenderId": "td-001",
  "netBidId": "nb-001",
  "enterpriseId": "ent-001",
  "decryptSort": 1,
  "isUnion": 0,
  "enterpriseIsUnion": 0,
  "sourceService": "crypto",
  "sourcePort": "8083",
  "payloadSha256": "sha256-of-normalized-payload",
  "payload": {
    "baseInfo": {},
    "tender": {
      "bidLetter": {},
      "bidForms": {},
      "bidEvalRules": {}
    },
    "versionInfo": {}
  }
}
```

处理规则：

- 唯一键：`(tenderId, netBidId)`
- 若首次接收：创建 `eval_project`、`eval_bidder` 及相关快照
- 若重复接收且 `payloadSha256` 相同：直接判定为幂等成功
- 若重复接收但 `payloadSha256` 不同：
  - 项目处于 `INIT` / `WAIT_EXPERT_SYNC` / `READY` 时允许覆盖，并写入 `eval_sync_log`
  - 项目已进入 `REVIEWING` 后拒绝覆盖，返回业务失败码

### 8.3 专家名单同步

`POST /api/eval/internal/sync/experts`

用途：

- 业务系统或评标管理端推送项目专家名单

建议请求体：

```json
{
  "tenderId": "td-001",
  "experts": [
    {
      "expertId": "exp-001",
      "expertName": "张三",
      "mobile": "13800000000",
      "identityNo": "3301************",
      "leaderFlag": false
    }
  ]
}
```

处理规则：

- 按 `tenderId + expertId` 幂等 upsert
- 若项目已开始评审，不允许删除已在场专家
- 组长可通过名单同步直接指定，也可通过选举产生；若两者冲突，以显式指定优先

### 8.4 启动指令

`POST /api/eval/internal/sync/start`

用途：

- 通知 `evaluation` 某个项目可以进入评标准备/启动阶段

建议请求体：

```json
{
  "tenderId": "td-001",
  "expectedBidderCount": 5,
  "allowMissingSyncedBidder": false,
  "deviationThresholdPercent": 20,
  "triggerUserId": "system",
  "triggerUserName": "系统",
  "remark": "评标准备完成"
}
```

处理规则：

- `expectedBidderCount` 用于校验数据是否齐备
- 当 `allowMissingSyncedBidder=false` 时：
  - 只有 `已同步投标人数 == expectedBidderCount` 才允许项目进入 `READY`
- 当 `allowMissingSyncedBidder=true` 时：
  - 允许项目以当前已同步投标人集合启动，但必须记录原因
- 已启动项目再次收到相同指令时按幂等成功处理

### 8.5 结果回传

评标结果通过 Interaction 机制回传业务系统。

一期新增 DTO 建议：

- `EvaluationResultCallbackRequest`
- `EvaluationBidderResultItem`
- `EvaluationNodeSummaryItem`

建议最小回传字段：

- `projectId`
- `tenderId`
- `bidEvalMethod`
- `winnerEnterpriseId`
- `winnerEnterpriseName`
- `rankingList`
- `nodeSummaries`
- `traceId`

## 十、文件处理策略

### 10.1 一期方案

评标所需 PDF 附件不沿用旧系统“解密目录直链下载”方式，而改为：

1. `crypto` 将 v9 payload 推给 `evaluation`
2. `evaluation` 从 payload 中提取 base64 文件内容
3. `evaluation` 调用 `file` 服务上传文件
4. `evaluation` 仅保存 `fileId/fileSha256/fileName/fileSize`
5. 前端访问 `evaluation` 文件代理接口，由后端使用内部凭证读取 `file`

### 10.2 原因

- 复用现有文件服务能力
- 避免评标系统自行维护磁盘目录协议
- 统一下载、鉴权、审计与文件元信息管理
- 消除旧系统 `/bidFile/download?tenderNo&fileType&fileName` 的路径耦合

## 十五、结论

一期评标接入应采用“**全新建设评标模块 + 复用 EleTender 现有公共能力 + 明确内部同步协议**”的方式落地。

关键不是模仿旧系统的字段和接口，而是保留其有效经验：

- 解密完成后逐条推送
- 同步接口必须幂等
- 以业务主键而不是页面状态做数据归并
- 文件和结果都要进入平台统一基础设施

按本版设计落地后，评标模块与 `crypto`、`file`、`interaction` 的边界会更清晰，也更符合 EleTender 当前代码体系。
