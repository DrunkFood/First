# 2026-03-17 最终招标文件生成需求整理

## 1. 背景

- 模块：`ele-tender-system/ele-tender-tender-document`
- 触发点：招标文件编制系统生成文件页的“生成采购文件数据包”按钮
- 当前现状：
  - 后端已经存在 `/api/tender-documents/generate` 与 `/api/tender-documents/generate/callback`
  - 当前 `generatePackage` 实现仍停留在一期占位阶段，默认实现只伪造产物，交互实现主要是把源采购文件与签章 PDF 打成 zip
  - 当前产物语义、命名与最终业务目标不一致，尚未形成正式的最终招标文件数据包

## 2. 本次目标

- 在招标文件编制系统后端生成正式的最终招标文件数据包
- 数据包基于当前编制单最新数据实时组装，不基于历史快照
- 最终数据包明文为 JSON，随后在招标文件编制系统内完成加密
- 加密后的正式数据包统一保存到文件服务
- 生成成功后，编制单进入完成态，不允许再次编辑，也不允许再次生成
- 生成成功后，额外生成一份可下载的带水印 PDF，正式名称为“采购文件编制信息”
- 统一回传时，回传签章 PDF 与最终数据包，不回传“采购文件编制信息”

## 3. 已确认业务约束

### 3.1 生成与状态

- 一个编制单只生成一份总包
- 项目级编制单：总包中包含项目下所有标段数据
- 标段级编制单：总包中只包含当前标段数据
- 生成成功后：
  - `TenderDocument.status = COMPLETED`
  - 编制单不可再次编辑
  - 不允许再次点击生成
- 编制完成时间等于数据包生成完成时间，需要落库记录

### 3.2 重复点击与并发

- 需要显式处理多次发起生成
- 状态流转约定为：
  - `DRAFT -> GENERATING -> COMPLETED`
  - 生成失败时：`GENERATING -> DRAFT`
- `GENERATING` 状态下再次点击，直接拦截
- `COMPLETED` 状态下再次点击，直接拦截

### 3.3 文件与存储

- 所有正式产物统一使用文件服务保存
- 招标文件编制模块只维护文件关联关系与业务状态，不单独持久化二进制文件
- 最终数据包需要长期保留，因为回传业务系统可能失败，后续存在多次回传
- “采购文件编制信息”也通过文件服务保存，供用户下载

### 3.4 回传

- `generate` 与 `callback` 必须解耦
- `generate` 负责生成并保存正式产物
- `callback` 负责把已保存的文件回传给业务系统
- 回传范围固定为：
  - `SIGNED_PDF`
  - `FINAL_PACKAGE_FILE`
- “采购文件编制信息”不参与回传

### 3.5 日志与留痕

- 生成全流程需要详细记录日志，便于后续查询
- 除控制台/traceId 日志外，还需要业务级生成记录
- 回传保留单独回传历史记录

### 3.6 文件命名规则

- 点击“生成文件”时，产物命名规则固定如下：
  - PDF 文件：`[上传的文件名不变][yyyyMMddHHmmss].pdf`
  - 最终数据包文件：`[项目编号]采购文件电子数据包[yyyyMMddHHmmss].HzctZbs`
- 时间戳精度到秒，格式统一为 `yyyyMMddHHmmss`
- `.HzctZbs` 后缀当前按本版规则使用，后续如需按业务系统切换，仍需保持命名主体规则不变

## 4. 最终数据包明文结构（V1 已确认版）

最终数据包加密前的 JSON 明文由招标文件编制系统后端生成，顶层结构固定为：

- `baseInfo`
- `tenders`
- `tenderDocumentSignPdf`
- `caKeysInfo`
- `settings`
- `versionInfo`

### 4.1 `baseInfo`

- `projectId`
- `projectName`
- `projectNo`
- `purchaserName` — 采购单位名称（v7 新增）
- `purchaseMethod` — 采购方式中文名，如"公开招标"（v7 新增）
- `bidEndTime` — 投标截止时间，格式 `yyyy-MM-dd HH:mm:ss`（v7 新增）
- `tendersInfo`
  - `tenderId`
  - `tenderName`
  - `tenderNo`
  - `tenderAmount` — 标段标的金额，BigDecimal(18,2)（v7 新增）
  - `purchaseContext` — 采购内容（v7 新增）

### 4.2 `tenders`

- 项目级编制单：数组包含全部标段编辑信息
- 标段级编制单：数组只包含当前标段编辑信息
- 每个标段节点至少包含：
  - `tenderId`
  - `tenderName`
  - `tenderNo`
  - `bidForms`
  - `bidEvalRules`

### 4.3 `bidEvalRules`

- `info`
  - `bidEvalMethod`
  - `reviewMode`
    - `ACTUAL`
    - `WEIGHT`
- 分类 key 固定使用枚举值：
  - `QUALIFICATION`
  - `CONFORMITY`
  - `DETAIL`
  - `CREDIT`
  - `TECHNICAL`
  - `BUSINESS`
- 其中：
  - `QUALIFICATION`、`CONFORMITY`、`DETAIL` 结构同类，采用通过制/规则列表模式
  - `CREDIT`、`TECHNICAL`、`BUSINESS` 采用打分制结构，包含 `totalScore`、`percentage`、`scoreRules`
- 规则树中字段名统一为 `objectiveType`

### 4.4 `tenderDocumentSignPdf`

- 承载签章后的招标文件 PDF 内容
- 字段至少包含：
  - `fileName`
  - `size`
  - `signedFileBase64`
  - `sha256`
- `signedFileBase64` 为字符串

### 4.5 `caKeysInfo`

- 保留以下字段：
  - `encryptOrder`
  - `userId`
  - `caId`
  - `caNo`
  - `publicKey`
- `encryptOrder`、`userId` 本版虽暂未使用，但按业务要求保留

### 4.6 `settings`

- 当前保留：
  - `signPosition.x`
  - `signPosition.y`

### 4.7 `versionInfo`

- `tenderDocumentFormatVersion`
- `tenderDocumentAppVersion`
- `tenderDocumentUniqueCode`

补充约束：

- `tenderDocumentUniqueCode` 由招标文件编制系统生成
- 生成规则采用纯系统码方式，不拼接业务编号

## 5. 需要落地的设计方向

- `generatePackage` 语义收敛为“生成唯一正式数据包”
- 引入真实的 `GENERATING` 中间状态
- 引入最终数据包文件角色 `FINAL_PACKAGE_FILE`
- 将“采购文件编制信息”从旧的编制回执概念升级为正式下载文件
- 将生成与回传彻底拆分
- 补齐生成记录查询能力

## 6. 风险点

- 当前 `generatePackage` 的实现与最终业务目标差距较大，需要同时调整服务、网关、文件角色、页面返回模型和测试
- 生成链路涉及文件下载、JSON 组装、加密、PDF 生成、文件服务上传与状态流转，必须保证失败时不会留下可见半成品状态
- 生成与回传解耦后，生成页与回传历史模型需要同步收敛，否则前端仍会沿用多包/旧文件角色语义
- 最终 JSON 中的 `bidForms` 仍待补充具体字段，实施时应保持 assembler 可扩展
