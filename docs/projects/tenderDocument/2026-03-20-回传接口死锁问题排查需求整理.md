# 需求整理（2026-03-20）- 回传接口偶发死锁排查

## 背景
- 接口：`POST /api/tender-documents/generate/callback?tenderDocumentId=48006`
- 现象：不是每次复现；有时成功，有时报 `Deadlock found when trying to get lock`
- 诉求：先调查原因并给出可选治理方案，待确认后再实施

## 现场日志关键信息
- 成功请求：
  - `traceId=a4c6d9740b9f48bf8be86b0a6a02de79`
  - `HTTP IN ... status=200 elapsedMs=4080`
- 失败请求：
  - `traceId=7b0b9ed2e11c437a94280f9457df15ec`
  - 异常：`org.springframework.dao.DeadlockLoserDataAccessException`
  - 报错 SQL（`TenderDocumentCallbackMapper.selectMaxRetryCountForUpdate`）：
    - `SELECT retry_count FROM td_tender_document_callback ... ORDER BY retry_count DESC, id DESC LIMIT 1 FOR UPDATE`
  - 调用链：`callbackAll -> callbackSignedFile -> callbackFile -> selectMaxRetryCountForUpdate`

## 代码定位与当前实现
- 回传入口：`TenderDocumentGenerationController.callbackAll`
- 服务实现：`TenderDocumentGenerationServiceImpl.callbackAll/callbackFile`
- 关键逻辑：
  1. `callbackAll` 使用 `@Transactional`，在一个事务里串行执行签章回传和数据包回传
  2. `callbackFile` 先调用远端回传网关，再执行 `select ... for update` 取最大重试次数，再插入回传记录
  3. 查询语句以 `tender_document_id + version_no + file_role (+ tender_id 条件)` 过滤，`ORDER BY retry_count DESC, id DESC LIMIT 1 FOR UPDATE`
- 表结构（`td_tender_document_callback`）现状：
  - 仅有索引：`(tender_document_id, version_no, file_role)`
  - 缺少 `tender_id/retry_count/id` 的联合索引覆盖

## 根因判断（高概率）
- 这是典型并发竞争下的行锁/间隙锁死锁，具备以下特征：
  1. 同一时段存在并发请求（日志出现两个 traceId 且时间重叠）
  2. `FOR UPDATE + ORDER BY + LIMIT` 在索引不充分时会扩大扫描与锁定范围
  3. 外层事务包裹两次回传与远程调用，锁持有时间较长，放大并发冲突窗口
- “不是每次复现”符合竞争条件问题：仅在并发时序撞上时触发

## 约束与目标
- 不能影响“回传留痕 + 重试次数”业务语义
- 不能因为数据库重试导致重复回传外部业务系统
- 优先选择低风险、可灰度、可快速回滚的方案
