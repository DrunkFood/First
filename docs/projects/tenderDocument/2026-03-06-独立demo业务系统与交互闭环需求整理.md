# 2026-03-06 独立 Demo 业务系统与交互闭环需求整理

## 1. 背景

- 当前仓库中的交互 starter、协议 DTO 与 `tender-document` 基础扩展点已经具备雏形。
- 但“电子标系统与业务系统真实交互闭环”仍未完成，`tender-document` 仍依赖默认占位 Gateway。
- 现有仓库内也没有一个可直接交付给业务系统开发同事参考的 starter 接入样例工程。

## 2. 本次目标

- 在当前仓库中完成 `ele-tender-tender-document` 与业务系统之间的正式交互闭环，替换默认占位实现。
- 在仓库根目录新增一个独立 Git 仓库形式的 demo 目录，提供一个“尽可能简单但可运行”的业务系统示例。
- 该 demo 系统用于给真实业务系统开发同事打样，重点展示：
  - 如何引入 `ele-tender-interaction-spring-boot-starter`
  - 如何配置 `base-url`、`file-base-url`、`app-key`、`app-secret`
  - 如何实现 5 个 SPI
  - 如何调用电子标系统获取 token 并生成招标文件编制页跳转地址
  - 如何接收签章 PDF / 数据包回传，并基于 `fileId` 做后续文件查询下载

## 3. 用户明确要求

- demo 必须是“独立的 Git 仓库”。
- 但 demo 目录可以物理上放在当前仓库下，采用嵌套 `git init` 方式隔离。
- demo 只需要内存样例数据，不需要数据库持久化。
- demo 代码和关键实现点要写明白注释，让业务系统开发能够知道真实项目需要替换哪些位置。

## 4. 交付边界

### 4.1 当前主仓库内需要完成

- `tender-document` 的正式同步 Gateway
- `tender-document` 的正式生成 Gateway
- `tender-document` 的正式回传 Gateway
- 正式出站调用能力、错误处理、关键日志追踪、最小集成测试
- 配套接入文档更新
- 主仓库 `.gitignore` 对 demo 目录做隔离，避免嵌套仓库误纳管

### 4.2 Demo 仓库内需要完成

- 独立 Spring Boot 示例应用
- 引入 `ele-tender-interaction-spring-boot-starter`
- 实现 5 个 SPI：
  - `InteractionIdentityService`
  - `InteractionProjectInfoService`
  - `InteractionBidRecordSchemeService`
  - `InteractionTenderPdfReceiveService`
  - `InteractionTenderPackageReceiveService`
- 提供一个“生成编制页跳转地址”的示例接口
- 提供一个“查看回传记录”的示例接口
- 提供清晰 README，说明启动前置条件、如何安装 starter、如何联调

## 5. 设计原则

- demo 保持最小可用，不做数据库、不做复杂权限、不做真实业务分层泛化。
- 不把 demo 纳入当前主仓库的 Maven reactor，避免污染主工程构建。
- demo 使用内存仓库与样例数据，但在 service / SPI 实现处写清楚真实项目的替换建议。
- `tender-document` 正式实现优先复用已有 interaction client 与文件服务能力，避免重复造轮子。
- 交互链路统一保留 `traceId`，并尽量补齐 `bizType`、`bizId`、`projectId`、`tenderId`、`fileId` 维度日志。

## 6. 风险与注意事项

- 嵌套 Git 仓库如果未忽略，容易污染主仓库 `git status`，必须先在根 `.gitignore` 中忽略。
- demo 作为示例工程，不应与主仓库模块产生源码级路径依赖，应通过 Maven 坐标依赖 starter。
- 若本地未先把 starter 安装到 Maven 本地仓库，demo 无法独立启动，README 需要明确这一点。
- 当前环境没有真正的“subagent/task tool”，本次按“协调-实现-复核”流程在当前会话内执行，但仍保持分任务、分阶段校验。
