# 评标系统接入设计

> 日期：2026-04-07
> 状态：设计确认

## 一、背景

公司已有评标系统（original-info-eval-total），需要在 EleTender 电子标平台基础上接入评标能力。方案为全新构建评标模块，参考现有系统的设计和流程，不做代码搬迁。

## 二、核心决策

| 维度 | 决策 |
|------|------|
| 定位 | 全新系统，参考现有评标系统设计 |
| 评标方法 | 第一期：最低评标价法 + 综合评分法，架构预留扩展 |
| 后端模块 | `ele-tender-evaluation`，端口 8084，表前缀 `eval_`，JDK 21 + Spring Boot 3.2.2 |
| 前端应用 | 独立应用 `ele-tender-evaluation-frontend`，Vue 3 + TS + Element Plus |
| 认证 | 共享 JWT 基础设施，新增 `type=EVALUATION`，用户数据在评标模块自管理 |
| 角色 | 专家（含组长标记）；暂无代理机构，预留扩展 |
| 数据协作 | crypto 解密后通过 HTTP API 逐条推送投标人数据，评标模块本地累积，收到启动信号后开始 |
| 结果输出 | 通过 Interaction 交互接口推送回业务系统 |
| 实时通信 | WebSocket |
| 少于三家 | 第一期支持 |
| 前端通信 | 评标前端只和评标后端通信（`/api/* → :8084`），文件由后端代理获取 |

## 三、系统架构

### 数据流

```
                    ┌──────────────┐
                    │  业务系统     │
                    └──┬───────┬───┘
            专家信息推送│       │启动评标信号
                       ▼       ▼
┌──────────┐  HTTP  ┌──────────────────┐  Interaction  ┌──────────────┐
│  crypto  │ ──────→│   evaluation     │ ─────────────→│  业务系统     │
│  :8083   │ 逐条推送│   :8084          │  结果回传      └──────────────┘
└──────────┘ 投标人  │                  │
                     │  ┌────────────┐  │  WebSocket  ┌─────────────────────┐
                     │  │ eval_ DB   │  │ ◄──────────→│ evaluation-frontend │
                     │  └────────────┘  │             │ :3001               │
                     └────────┬─────────┘             └─────────────────────┘
                              │ HTTP（内部凭证）
                              ▼
                     ┌──────────────┐
                     │  file :8081  │  (文件下载代理)
                     └──────────────┘
```

### 认证隔离

```
JWT type=INTERNAL   → support / file / tender-document / crypto（互认）
JWT type=EXTERNAL   → interaction 交互接口
JWT type=EVALUATION → evaluation 专用（其他服务拒绝）
```

## 四、评标业务流程

### 项目生命周期

```
INIT → EXPERT_PREPARE → REVIEWING → SUBMIT_RESULT → FINISH
```

- INIT：接收 crypto 推送的投标人数据，逐条累积
- EXPERT_PREPARE：收到启动信号后，专家同步、选举组长
- REVIEWING：评审节点循环（打分/通过 → 确认 → 汇总 → 推进）
- SUBMIT_RESULT：结果确认，生成排名
- FINISH：回传业务系统

### 评审节点

**最低评标价法：** 资格审查(PASS) → 符合性评审(PASS) → 详细评审(PASS) → 结果

**综合评分法：** 资格审查(PASS) → 符合性评审(PASS) → 资信评审(SCORE) → 技术评审(SCORE) → 商务评审(SCORE) → 结果

### 单节点内部流程

专家各自评审 → 专家确认提交 → 组长查看汇总（检测 >20% 偏差）→ 组长确认 → 推进下一节点

### 少于三家

有效投标人不足 3 家时触发专家投票，选项：继续评标 / 废标 / 重新招标

## 五、数据模型

### 核心表（eval_ 前缀）

| 表名 | 用途 |
|------|------|
| `eval_project` | 评标项目主表（项目信息、评标办法、阶段、当前节点） |
| `eval_bidder` | 投标人（名称、信用代码、标录 JSON、投标函 JSON、状态、排序） |
| `eval_bidder_file` | 投标人文件（分类、文件名、路径、SHA256） |
| `eval_bid_eval_rules` | 评审规则 JSON 快照 |
| `eval_user` | 评标系统用户（专家） |
| `eval_project_expert` | 专家-项目关联（组长标记、阶段、进度） |
| `eval_expert_election` | 组长选举记录 |
| `eval_expert_result` | 专家个人评审结果（通过/评分/偏差标记） |
| `eval_result_summary` | 节点汇总结果 |
| `eval_final_ranking` | 最终排名 |
| `eval_vote` | 少于三家投票 |
| `eval_sync_log` | 数据同步记录 |

### 设计要点

- 评审规则存完整 JSON 快照，不拆关系表
- 投标人文件（base64 PDF）同步时解码存文件，记录路径
- 标录数据存完整 bidForms JSON（含 schemeContent + bidFormData）

## 六、接口设计

### 数据接收（crypto/业务系统 → evaluation）

- `POST /api/eval/sync/bidder` — 接收单个投标人解密数据
- `POST /api/eval/sync/start` — 启动评标信号

### 专家管理

- `POST /api/eval/expert/login` — 专家登录
- `GET/POST /api/eval/project/experts` — 项目专家列表/添加
- `POST /api/eval/election/vote` — 组长选举投票

### 评审流程

- `GET /api/eval/review/bidders` — 当前节点待评审投标人
- `POST /api/eval/review/submit` — 提交评审结果
- `POST /api/eval/review/confirm` — 确认提交
- `GET /api/eval/review/summary` — 汇总查看
- `POST /api/eval/review/summary/confirm` — 确认汇总
- `POST /api/eval/review/next-node` — 推进下一节点
- `POST /api/eval/review/vote` — 少于三家投票

### 数据查询

- `GET /api/eval/project/info` — 项目信息和状态
- `GET /api/eval/bidder/{id}/forms` — 标录数据
- `GET /api/eval/bidder/{id}/file/{category}` — 文件下载（代理）
- `GET /api/eval/result/final` — 最终结果

### WebSocket

- `/ws/eval/project/{projectId}` — 项目实时通信房间

### 结果回传

通过 Interaction 机制回调业务系统。

## 九、数据来源确认

crypto 解密产物（v9 格式）能提供评标所需的核心数据：

- 项目/标段基本信息 ← baseInfo
- 投标人信息 ← bidLetter
- 标录方案和数据 ← bidForms（schemeContent + bidFormData）
- 评审规则树 ← bidEvalRules
- 投标人附件 PDF ← 各评审分类的 file 字段
- 版本和防篡改信息 ← versionInfo

剩余需业务系统/评标模块自行管理的数据：
- 专家信息（业务系统推送或评标模块管理）
- 项目级配置（评标时间等，启动评标时作为参数传入）
