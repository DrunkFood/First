# 真实短信网关接入设计

## 背景

当前支撑中心 `ele-ai-tender-support` 已具备短信验证码基础链路：生成验证码、Redis 5 分钟缓存、60 秒发送限流、`sup_sms_code` 审计记录、验证码登录和重置密码校验。现有 `SmsServiceImpl` 仍是模拟发送，接口会把验证码明文返回给前端，前端再弹出测试提示。

本次改造目标是接入公司短信网关，使验证码通过真实短信发送，并去掉前端明文展示验证码的测试行为。

## 网关约定

短信网关使用 HTTP POST 表单提交，配置前缀为 `msg`。

请求地址由配置提供：

```yaml
msg:
  username: ${MSG_USERNAME:}
  pwd: ${MSG_PWD:}
  extend: ${MSG_EXTEND:}
  url: ${MSG_URL:}
  isformal: ${MSG_ISFORMAL:false}
```

请求参数：

| 参数 | 说明 |
| --- | --- |
| `username` | 网关账号 |
| `password` | 网关密码 |
| `mobile` | 接收手机号，当前业务每次发送一个手机号 |
| `content` | 短信内容，UTF-8 表单编码 |
| `extend` | 网关扩展号 |
| `level` | 固定传 `1` |

响应按 `&` 分隔为键值对，`result=0` 视为发送成功。响应为空、无法解析、`result` 非 `0` 或 HTTP 调用异常，均视为发送失败。

## 方案对比

### 方案一：在 `SmsServiceImpl` 内直接调用网关

改动最少，但验证码生成、限流、持久化和外部网关调用会继续混在一个类里。后续如果更换供应商或增加测试替身，维护成本较高。

### 方案二：新增短信网关客户端

新增 `SmsGatewayProperties` 和 `SmsGatewayClient`，由客户端封装配置、表单请求、响应解析和正式/非正式发送开关。`SmsServiceImpl` 继续只负责编排验证码生命周期。该方案边界清晰，便于单元测试和后续替换网关。

### 方案三：引入第三方短信 SDK

适合云厂商短信服务，但当前网关是公司 HTTP 接口。引入 SDK 不能直接解决该网关协议，反而增加依赖。

推荐采用方案二。

## 详细设计

### 后端结构

在 `ele-ai-tender-support` 中新增短信网关配置和客户端：

- `SmsGatewayProperties`：绑定 `msg.*` 配置，包含 `username`、`pwd`、`extend`、`url`、`isformal`。
- `SmsGatewayClient`：提供 `sendCode(phone, code, scene)` 方法，生成短信内容并调用网关。
- `SmsServiceImpl`：保留手机号校验、60 秒限流、过期旧验证码、生成验证码、Redis 缓存、数据库审计和验证码校验流程。

发送顺序调整为：

1. 校验发送频率。
2. 过期旧验证码。
3. 生成 6 位验证码。
4. 调用 `SmsGatewayClient` 发送短信。
5. 发送成功后写入 Redis、写入 `sup_sms_code`、设置 60 秒限流。
6. 发送失败时不保存验证码、不设置限流，返回业务异常。

这样可以避免用户收到失败提示后，系统内却存在一个可用验证码。

### 短信内容

登录场景：

```text
您的验证码是：${code}，5分钟内有效，请勿泄露。
```

重置密码场景：

```text
您正在重置密码，验证码是：${code}，5分钟内有效，请勿泄露。
```

未知场景使用通用验证码文案。

### 正式发送开关

`msg.isformal=false` 时不调用外部网关，只记录脱敏日志并返回发送成功，便于本地开发和测试。

`msg.isformal=true` 时必须具备完整网关配置。配置缺失、HTTP 异常或网关返回失败时抛出 `BusinessException("验证码发送失败，请稍后重试")`。

日志要求：

- 不打印 `pwd`。
- 不在正式发送日志中打印验证码明文。
- 允许记录手机号、场景、网关返回码和失败原因。

### 前端调整

`ele-ai-tender-frontend` 登录页和重置密码弹窗中的发码成功提示改为：

```text
验证码已发送，请注意查收
```

前端不再依赖后端返回验证码明文。为了兼容后端返回结构，`authApi.sendSmsCode` 可以继续声明为 `Promise<string>` 或调整为 `Promise<void>`；推荐调整为 `Promise<void>`，调用方不读取返回值。

### 接口返回

`/api/auth/send-sms-code` 不再返回验证码明文，成功时返回空成功响应：

```json
{"code":0,"message":"success","data":null}
```

若当前 `Result.success()` 的序列化格式不同，以项目统一响应结构为准。

### 安全补强

本次聚焦真实短信接入，同时保留现有限流和一次性使用策略。验证码登录的场景隔离仍建议在实现中同步修正：Redis key 从仅按手机号存储调整为按 `scene:phone` 存储，登录校验只验证 `LOGIN` 场景，重置密码只验证 `RESET_PWD` 场景，避免不同场景验证码互相复用。

错误次数限制可作为后续增强，不纳入本次必要范围。

## 测试计划

后端单元测试：

- `isformal=false` 时不调用外部网关，发码成功并写 Redis/数据库。
- `isformal=true` 且网关返回 `result=0` 时发码成功。
- 网关返回失败、空响应或调用异常时抛出业务异常，且不写 Redis 验证码。
- 响应解析支持 `result=0&msg=...` 形式。
- `LOGIN` 和 `RESET_PWD` 场景验证码互不复用。

前端验证：

- 登录页获取验证码后只提示“验证码已发送，请注意查收”。
- 重置密码弹窗获取验证码后只提示“验证码已发送，请注意查收”。
- 手机验证码登录成功后仍正常写入登录态并跳转。

构建验证：

- 后端执行 `ele-ai-tender-support` 相关测试。
- 前端执行 `npm run build`。

## 配置与部署

仓库内配置只保留环境变量占位。真实账号、密码、网关地址和正式发送开关应放在服务器环境变量或本地覆盖文件：

```yaml
msg:
  username: ${MSG_USERNAME:}
  pwd: ${MSG_PWD:}
  extend: ${MSG_EXTEND:}
  url: ${MSG_URL:}
  isformal: ${MSG_ISFORMAL:false}
```

本地开发默认 `MSG_ISFORMAL=false`。测试或生产环境根据部署要求显式设置为 `true`。
