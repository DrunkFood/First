# 招投标文件格式 v9 适配

> 日期：2026-04-07
> 状态：设计确认

## 背景

招投标文件格式从 v8 升级到 v9，核心变更是 `bidForms` 从固定字段结构改为 `schemeContent`（标录方案）+ `bidFormData`（标录数据）的动态结构。需要适配相关模块代码。

## v9 关键变更

1. **招标文件 `bidForms`**：只包含 `schemeContent`（标录方案定义，JSON 数组字符串）
2. **投标文件 `bidForms`**：包含 `schemeContent` + `bidFormData`（投标方填写的标录数据）
3. **投标文件 `bidEvalRules`**：各评审分类（QUALIFICATION/CONFORMITY/TECHNICAL/BUSINESS）补充 `file` 字段，新增 `OTHER` 分类（仅含 file）— 这是投标端独有的，招标编制侧不涉及

## 改造范围

### 1. BidRecordSchemeResponse 清理（ele-tender-common-interaction）

移除 `schemeId`、`schemeName`、`schemeVersion` 三个无用字段，只保留 `schemeContent`。

### 2. FinalPackageDataAssembler 适配（ele-tender-tender-document）

当前实现将 BidRecordSchemeResponse 整体写入 `bidForms`，导致多出 schemeId/schemeName/schemeVersion。清理 DTO 后自然解决。

### 3. dev-tools mock 生成器适配（ele-tender-dev-tools）

- `TenderDocumentGenerator`：`bidForms` 改为 `{ "schemeContent": "[...]" }`
- `BidDocumentGenerator`：`bidForms` 改为 `{ "schemeContent": "[...]", "bidFormData": { ... } }`

### 4. 重新生成招投标文件

改造完成后使用 dev-tools CLI 重新生成招标文件和投标文件，验证输出格式符合 v9 规范。

## 不涉及的模块

- `ele-tender-crypto`：解密产物是完整 JSON 字符串（`bid_record_data_json`），不做结构化解析，v9 格式变化不影响
- `bidEvalRules` 的 file 字段和 OTHER 分类：投标端独有，招标编制侧不涉及

## 验证方式

- dev-tools 生成招标文件，检查 bidForms 结构只有 schemeContent
- dev-tools 生成投标文件，检查 bidForms 结构有 schemeContent + bidFormData
- 完成后 /simplify 检查代码质量
- 完成后 /codex:adversarial-review 进行 code review
