# 招标文件编制系统正式设计文档

## 1. 文档说明

- 文档日期：2026-03-04
- 适用范围：`ele-tender-system/ele-tender-tender-document`
- 目标：固化招标文件编制系统当前确认后的正式后端设计，作为后续实现、联调、测试、文档和异常码维护的统一基线。

## 2. 一期建设目标

- 在现有 `ele-tender-system` 体系内建设独立的招标文件编制服务。
- 面向前端提供按页面组织的接口，而不是按后端内部数据模型直接暴露接口。
- 支持业务系统跳转进入、项目首创人锁、固定步骤编制、实时数据同步、文件绑定、评审规则配置、生成文件和统一回传。
- 对公开类项目按项目级编制，对邀请类项目按标段级编制。
- 一期先完成流程壳子、页面接口、核心数据模型、文件闭环和评审规则能力，不展开检查项自动校验引擎和最终数据包格式细节。

## 3. 系统规范

### 3.1 统一返回格式

所有对前端接口统一返回 `Result<T>`，结构以当前项目实际实现为准：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {},
  "timestamp": 1700000000000
}
```

固定规则：
- 成功时：
  - `code = 200`
  - `message` 默认使用“操作成功”，必要时可返回更具体的成功提示
  - `data` 返回业务对象
- 失败时：
  - 仍返回 `Result<T>` 结构
  - `code != 200`
  - `message` 返回业务错误信息
  - `data` 默认为 `null`
- 页面接口的 `data` 尽量返回对象，不直接返回裸数组、裸字符串。
- 前端处理业务失败时，以响应体中的 `code` 为主，不以 HTTP 200/500 作为唯一判断依据。

### 3.2 当前全局异常处理约束

根据现有项目实现，当前系统异常处理规则如下：

- `AuthException`：
  - HTTP 状态码：`200`
  - 返回：`Result.fail(e.getCode(), e.getMessage())`
- `BusinessException`：
  - HTTP 状态码：`200`
  - 返回：`Result.fail(e.getCode(), e.getMessage())`
- 参数校验异常：
  - HTTP 状态码：`200`
  - 返回：`code = 400`
- 未兜底系统异常：
  - HTTP 状态码：`500`
  - 返回：`Result.fail("系统异常，请稍后重试")`

因此：
- 业务失败不依赖 HTTP 4xx/5xx。
- 前端联调必须按 `Result.code` 解析业务结果。

### 3.3 异常码规范

当前项目已存在的异常码区间如下：

- 通用：
  - `200` 成功
  - `500` 通用失败
- 参数相关：
  - `400` 参数错误
  - `401` 未授权
  - `403` 无权限访问
  - `404` 资源不存在
  - `405` 方法不允许
- 用户相关：
  - `1001-1999`
- 角色权限相关：
  - `2001-2999`
- 接入系统相关：
  - `3001-3999`
- 版本管理相关：
  - `4001-4999`
- 文件相关：
  - `5001-5999`

招标文件编制系统新增异常码，统一预留：

- `6001-6999`：`TenderDocument` 业务域

### 3.4 招标文件编制系统异常码建议

一期建议按下面的编码维护招标文件编制系统异常码：

| 编码 | 常量建议 | 含义 |
| --- | --- | --- |
| 6001 | `TENDER_DOCUMENT_NOT_FOUND` | 编制单不存在 |
| 6002 | `PROJECT_LOCKED` | 当前项目已由首创人锁定 |
| 6003 | `TENDER_DOCUMENT_NOT_EDITABLE` | 当前编制单状态不允许编辑 |
| 6004 | `ENTRY_BASIC_INFO_SYNC_FAILED` | 入口同步项目信息失败 |
| 6005 | `BASIC_INFO_NOT_SYNCED` | 基本信息尚未完成同步 |
| 6006 | `BID_RECORD_NOT_SYNCED` | 标录信息尚未完成同步 |
| 6007 | `STEP_NOT_FOUND` | 步骤不存在 |
| 6008 | `STEP_COMPLETE_NOT_ALLOWED` | 当前步骤不允许完成并进入下一步 |
| 6009 | `RULE_NOT_FOUND` | 评审规则不存在 |
| 6010 | `RULE_VALIDATION_FAILED` | 评审规则校验失败 |
| 6011 | `TENDER_ID_REQUIRED` | 当前操作必须传入标段ID |
| 6012 | `FILE_BINDING_NOT_FOUND` | 当前步骤缺少可用文件绑定 |
| 6013 | `GENERATION_NOT_ALLOWED` | 当前编制单不允许生成文件 |
| 6014 | `GENERATED_FILE_MISSING` | 缺少已生成产物文件 |
| 6015 | `CALLBACK_NOT_ALLOWED` | 当前编制单不允许回传 |

维护规则：
- 新增业务异常码前，先补充到系统规范文档。
- 避免重复使用同一个编码表达不同语义。
- 避免继续大量直接抛默认 `500` 的 `BusinessException("中文文本")`。
- 优先使用“固定编码 + 可读 message”的形式。

### 3.5 URL 设计规范

- 不在路径中使用 `page`。
- 路径参数统一放在最后。
- 动作型接口使用 `资源/动作/{id}` 风格，不使用 `/{id}/动作`。
- 面向前端的接口按页面组织，不直接暴露后端内部步骤快照模型。

## 4. 核心业务约束

### 4.1 访问与安全

- 编制系统无独立登录页，从业务系统单点跳转进入。
- 是否具备编制权限由业务系统控制。
- 项目访问受“首创人锁”控制。
- 同一 `projectId` 第一次进入编制流程的用户成为该项目唯一可查看、可编辑的编制人。
- 后续访问必须同时匹配：
  - `appKey`
  - `enterpriseCode`
  - `userId`

### 4.2 编制粒度

- 公开类项目：按项目级编制。
- 邀请类项目：按标段级编制。
- `compileScope` 为后端内部字段。
- 基本信息同步结果至少需要包含 `projectType`，用于表达公开类/邀请类。
- 若业务系统能直接返回 `compileScope`，电子标系统优先使用该字段。
- 若未直接返回 `compileScope`，电子标系统允许根据 `projectType` 映射：
  - 公开类 -> `PROJECT`
  - 邀请类 -> `TENDER`

### 4.3 TenderDocument 与项目、标段关系

- `TenderDocument` 必定归属于一个 `projectId`。
- `TenderDocument` 的实际归属粒度由 `compileScope` 决定：
  - `PROJECT`：对应整个项目
  - `TENDER`：对应项目下某一个标段
- `compileScope = PROJECT` 时：
  - `tenderId` 为空
- `compileScope = TENDER` 时：
  - `tenderId` 必填

可以直接理解为：
- 公开类：`TenderDocument = 项目编制单`
- 邀请类：`TenderDocument = 标段编制单`

### 4.4 版本规则

- 一期采用“主版本 + 草稿”模型。
- 生成成功后固化完成版本。
- “重新编制”时从最近完成版本复制出新草稿，步骤状态全部重置。

## 5. 入口规则

### 5.1 入口接口

- `POST /api/tender-documents/entry`

请求只保留必选参数：
- `bizType`
- `bizId`
- `projectId`
- `tenderId`

### 5.2 入口处理流程

1. 校验项目锁，项目锁始终按 `projectId`
2. 直接调用统一的“基本信息同步能力”
3. 从同步结果中取得：
   - 项目信息
   - 标段信息
   - `projectType`
   - `compileScope`（如有）
4. 根据 `compileScope` 命中或创建编制单：
   - `PROJECT`：按 `bizType + bizId + projectId` 命中或创建
   - `TENDER`：按 `bizType + bizId + projectId + tenderId` 命中或创建
5. 返回最小入口结果

约束：
- 项目信息唯一来源就是“基本信息同步能力”。
- `entry` 不单独再定义第二套项目信息获取接口。
- 入口命中编制单时，优先使用同步结果中的 `compileScope`；缺省时再根据 `projectType` 推导。
- 如果同步失败，直接报错，不创建编制单。

### 5.3 入口返回

入口返回最小结果：

- `tenderDocumentId`
- `projectId`
- `tenderId`
- `status`
- `currentStepCode`
- `versionNo`

前端后续只使用 `tenderDocumentId` 调其他页面接口。

## 6. 流程设计

### 6.1 固定步骤

1. `BASIC_INFO` 基本信息录入
2. `PURCHASE_FILE` 采购文件编制
3. `BID_RECORD` 开标标录设置
4. `EVALUATION_RULE` 评审规则设置
5. `CHECK_ITEMS` 检查项
6. `GENERATE_PACKAGE` 生成文件

### 6.2 步骤状态

- `PENDING` 未开始
- `IN_PROGRESS` 进行中
- `COMPLETED` 已完成

### 6.3 编制单状态

- `DRAFT` 编制中
- `GENERATING` 生成中
- `COMPLETED` 已生成完成

规则：
- `COMPLETED` 直接表示查看模式。
- 不单独维护 `mode` 字段。
- “完成并进入下一步”负责完整校验、标记当前步骤完成、推进下一步。
- 最后一步不通过“完成并进入下一步”结束，而由“生成文件”动作收口。

## 7. 页面接口设计

### 7.1 概览接口

- `GET /api/tender-documents/overview（query: tenderDocumentId）`

返回：
- `tenderDocumentId`
- `status`
- `currentStepCode`
- `versionNo`
- `editable`
- `active`
- `stepList`

`stepList` 每项：
- `stepCode`
- `stepName`
- `stepOrder`
- `stepStatus`
- `active`

### 7.2 基本信息录入

接口：
- `GET /api/tender-documents/basic-info（query: tenderDocumentId）`
- `POST /api/tender-documents/basic-info/sync（query: tenderDocumentId）`

返回：
- `projectInfo`
- `tenderList`（每个标段对象内包含 `bidRecord`）
- `lastSyncTime`

### 7.3 采购文件编制

接口：
- `GET /api/tender-documents/purchase-file（query: tenderDocumentId）`
- `POST /api/tender-documents/purchase-file/bind（query: tenderDocumentId）`
- `DELETE /api/tender-documents/purchase-file（query: tenderDocumentId）`
- `GET /api/tender-documents/purchase-file/signed（query: tenderDocumentId）`
- `POST /api/tender-documents/purchase-file/signed/bind（query: tenderDocumentId）`
- `DELETE /api/tender-documents/purchase-file/signed（query: tenderDocumentId）`

返回：
- `fileList`

`fileList` 每项：
- `tenderId`
- `tenderName`
- `fileId`
- `fileName`
- `fileSize`
- `contentType`
- `fileSha256`

说明：
- 前端先上传到文件系统。
- 编制系统只保存文件绑定关系。
- 删除本质是解绑，不删除文件系统中的原文件。
- 采购文件步骤完成前，必须同时存在源采购文件和签章文件。

### 7.4 开标标录设置

接口：
- `GET /api/tender-documents/bid-record（query: tenderDocumentId）`
- `POST /api/tender-documents/bid-record/sync（query: tenderDocumentId）`

返回：
- `projectInfo`
- `tenderList`
- `lastSyncTime`

说明：
- 返回结构化对象，不返回原始 JSON 字符串。

### 7.5 评审规则设置

接口：
- `GET /api/tender-documents/evaluation-rules（query: tenderDocumentId）`
- `GET /api/tender-documents/evaluation-rules/item（query: tenderDocumentId,tenderId,nodeCategory）`
- `PUT /api/tender-documents/evaluation-rules/item（query: tenderDocumentId,tenderId,nodeCategory）`
- `POST /api/tender-documents/evaluation-rules/copy（query: tenderDocumentId）`

页面概览返回：
- `evalMethod`
- `tenderList`
- `nodeCategoryList`

节点详情返回：
- `tenderId`
- `tenderName`
- `nodeCategory`
- `reviewMode`
- `scoreType`
- `totalScore`
- `weightRate`
- `treeToPageData`

### 7.6 检查项

接口：
- `GET /api/tender-documents/check-items（query: tenderDocumentId）`

返回：
- `itemList`

每项：
- `itemCode`
- `itemName`
- `passed`
- `message`

说明：
- 一期先做展示接口，占位后续真正检查逻辑。

### 7.7 生成文件

接口：
- `GET /api/tender-documents/generate（query: tenderDocumentId）`
- `POST /api/tender-documents/generate（query: tenderDocumentId）`
- `GET /api/tender-documents/generate/records（query: tenderDocumentId）`
- `POST /api/tender-documents/generate/callback（query: tenderDocumentId）`

页面返回：
- `status`
- `versionNo`
- `signedFile`
- `finalPackageFile`
- `compileInfoFile`
- `compileCompleteTime`
- `latestGenerateRecord`
- `callbackHistory`

说明：
- 生成接口只负责生成，不负责回传。
- 统一回传接口只回传签章文件和最终数据包，不回传 `COMPILE_INFO_PDF`。
- 前端只有一个统一“回传文件”按钮。
- 后端统一回传接口内部拆成两段：
  - 回传签章文件 PDF
  - 回传采购文件数据包
- 回传记录仍按文件类型分别落库。

### 7.8 完成并进入下一步

接口：
- `POST /api/tender-documents/complete-and-next（query: tenderDocumentId）`

请求：
- `stepCode`

返回：
- 概览对象

## 9. 文件与生成规则

- 采购文件、签章文件均由前端先上传至文件系统，再绑定到编制单。
- 公开类项目：项目级产物。
- 邀请类项目：标段级产物。
- 生成成功后至少产出：
  - 签章文件记录
  - 采购文件数据包
  - 编制信息 PDF
- 编制信息 PDF 至少包含：
  - 项目信息
  - 数据包 SHA-256
  - 生成时间
