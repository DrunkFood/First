# 文件后缀校验 + File 服务兼容性修复

## 背景

Adversarial review 发现两个问题：
1. 接入系统的 `tender_document_suffix` / `bid_document_suffix` 字段无校验，可注入路径穿越字符
2. 自定义后缀可成功保存到 `sup_access_system`，但 file 服务 `allowed-types` 白名单不包含该后缀，导致上传时被拒绝

## 修复方案

### 1. 后缀格式校验

在 `FileConstants` 中新增静态方法 `validateDocumentSuffix(String suffix)`：
- 正则：`^\.[A-Za-z0-9]{1,31}$`（以 `.` 开头，仅字母数字，最长 32 字符）
- 校验通过返回原值，失败抛 `IllegalArgumentException`
- 在 `ExternalSystemServiceImpl.createSystem()` / `updateSystem()` 中保存前调用
- `null` 或空字符串视为"使用默认值"，跳过校验

### 2. File 服务自动放行已注册后缀

#### 数据流

```
Support 保存后缀 → 汇总所有已注册后缀 → 写入 Redis Set
                                          ↓
File 服务上传 → 静态白名单校验 → 不匹配 → 本地内存缓存 → 缓存命中? → 放行
                     ↓                        ↓ miss
                   匹配 → 放行              Redis Set 查询 → 刷新缓存
```

#### Redis 结构

- Key: `ele-tender:registered-suffixes`
- Type: Set
- Values: 所有已配置的自定义后缀（如 `.CustomZbs`, `.CustomTbs`）
- 无 TTL（由 Support 主动维护）

#### Support 端（写入方）

在 `ExternalSystemServiceImpl` 中：
- `createSystem()` / `updateSystem()` 保存成功后，调用 `refreshRegisteredSuffixes()`
- `refreshRegisteredSuffixes()`: 查询所有 `sup_access_system` 中非空的 `tender_document_suffix` 和 `bid_document_suffix`，去重后写入 Redis Set（先 DEL 再 SADD，用 pipeline 保证原子性）
- `deleteSystem()` 后同样触发刷新

#### File 端（读取方）

在 `FileStorageConfig` 或新建 `AllowedTypesResolver` 中：
- 维护一个本地内存缓存（`Set<String>` + 上次刷新时间戳）
- TTL: 5 分钟
- 校验逻辑：`staticAllowedTypes.contains(suffix) || dynamicRegisteredSuffixes.contains(suffix)`
- 缓存 miss 或过期时从 Redis `SMEMBERS ele-tender:registered-suffixes` 刷新
- 高 QPS 下热路径为本地 `Set.contains()`，无网络开销

#### `LocalFileStorageServiceImpl.validateFile()` 改动

将当前的白名单校验逻辑改为调用 `AllowedTypesResolver.isAllowed(filename)`，内部合并静态白名单 + 动态注册后缀。

## 涉及文件

| 文件 | 改动 |
|------|------|
| `ele-tender-common/.../FileConstants.java` | 新增 `validateDocumentSuffix()` |
| `ele-tender-support/.../ExternalSystemServiceImpl.java` | 创建/更新/删除时校验后缀 + 刷新 Redis |
| `ele-tender-file/.../AllowedTypesResolver.java` | 新建，合并静态白名单 + Redis 动态后缀 |
| `ele-tender-file/.../LocalFileStorageServiceImpl.java` | 校验逻辑改用 `AllowedTypesResolver` |
| `ele-tender-file/.../FileStorageConfig.java` | 无变动，仍提供静态白名单 |

## 不做的事

- 不引入 Caffeine 依赖，用简单的 `volatile Set` + 时间戳即可满足需求
- 不做 Pub/Sub 实时通知，5 分钟 TTL 延迟可接受
- 不改 `resolve*Suffix()` 方法的读取逻辑，存入端校验已足够
- 不新增 DB migration 工具，沿用项目现有 init.sql 模式
