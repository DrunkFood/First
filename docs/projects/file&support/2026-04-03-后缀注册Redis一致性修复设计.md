# 后缀注册 Redis 一致性修复设计

> 创建日期：2026-04-03
> 来源：Codex adversarial review 发现

---

## 背景

Codex review 指出后缀可配置化功能存在两个一致性问题：

1. `ExternalSystemServiceImpl` 的 CRUD 操作在 DB 写入后刷新 Redis，无事务保护，Redis 失败会导致 DB-Redis 不一致；DEL+SADD 非原子操作存在中间空窗期
2. `AllowedTypesResolver` 在 Redis 读取失败时仍推进 `lastRefreshTime`，导致缓存被锁定 5 分钟无法自愈

## 修复 1：ExternalSystemServiceImpl DB+Redis 一致性

### 变更

- `createSystem`、`updateSystem`、`deleteSystem` 加 `@Transactional(rollbackFor = Exception.class)`
- Redis 刷新改为 `TransactionSynchronization.afterCommit()` 回调，DB 回滚时不执行
- after-commit 中 Redis 刷新失败 catch + log.error，不抛出（DB 已提交是事实，下次操作会自愈）
- `DEL + SADD` 改为写入临时 key + `RENAME` 原子替换，消除中间空窗期
- suffixes 为空时直接 `DELETE` 主 key

### 影响文件

- `ele-tender-system/ele-tender-support/src/main/java/com/jy/eletender/support/service/impl/ExternalSystemServiceImpl.java`

## 修复 2：AllowedTypesResolver 缓存 TTL 修复

### 变更

- Redis 读取成功时才更新 `lastRefreshTime`
- Redis 读取失败时记录 `lastFailTime`，保留旧缓存，不推进 `lastRefreshTime`
- 新增 `RETRY_COOLDOWN_MS`（1 秒），避免 Redis 持续不可用时每个请求都打一次
- Redis 恢复后第一个请求即可刷新缓存

### 影响文件

- `ele-tender-system/ele-tender-file/src/main/java/com/jy/eletender/file/config/AllowedTypesResolver.java`

## 不修复：读侧后缀校验

Codex 还指出 DB 后缀读侧未校验的问题。经分析，写入侧已通过 `FileConstants.validateDocumentSuffix()` 严格校验（正则 `^\.[A-Za-z0-9]{1,31}$`），不合法后缀不可能入库，读侧无需重复校验。

## 验证

1. `mvn -pl ele-tender-support -am clean test` — 事务 + Redis 刷新测试
2. `mvn -pl ele-tender-file -am clean test` — 缓存 TTL 行为测试
