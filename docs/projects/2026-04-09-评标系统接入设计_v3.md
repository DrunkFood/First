# 评标系统接入设计 v3

> 日期：2026-04-09
> 状态：设计修订稿
> 适用范围：EleTender 平台一期评标能力接入
> 替代关系：本稿替代 `2026-04-07-评标系统接入设计.md`（v1）和 `2026-04-08-评标系统接入设计_v2.md`（v2）

## 一、修订背景

v1 确立了全新建设评标模块的总体方向，v2 补全了幂等设计、启动前置条件和参考边界，但两版仍存在以下问题：

- 节点状态设计凭空构造了线性枚举模型（v2 的 6 状态），未核对原评标系统的实际实现
- 项目生命周期缺少 `EVAL_SETTING` 阶段，丢失了参数配置和节点链初始化的业务环节
- 遗漏了原系统中"汇总"与"确认汇总"是两步独立操作的关键逻辑
- 未识别评审节点的模板化机制（按评标办法动态配置节点链）
- 未区分通过制（PASS）和打分制（SCORE）两种评审类型
- 未涉及重评（reReview）和重置（reset）机制
- 未给出 crypto 解密产物到评标字段的显式映射（v1 有，v2 丢失）

本版基于对原评标系统（`original-info-eval-total`）核心代码的逐文件分析，结合 v1 的架构清晰度和 v2 的协议完整度，重新收敛设计。

## 三、核心设计结论

| 维度 | 结论 |
|------|------|
| 后端模块 | 新建 `ele-tender-evaluation`，端口 `8084`，表前缀 `eval_` |
| 前端应用 | 新建 `ele-tender-evaluation-frontend`，端口 `3001` |
| 评标对象粒度 | 一个 `tenderId` 对应一个评标项目 |
| 接入协议来源 | 以 EleTender v9 解密结果为准，不复用原系统字段名 |
| 数据接入模式 | `crypto` 逐条推送投标人数据；业务系统推送专家与启动指令 |
| 节点状态模型 | 参考原系统：双标志位（summary + summaryResult）+ 专家个人 done 状态 |
| 项目生命周期 | `INIT → EVAL_SETTING → EXPERT_PREPARE → REVIEWING → SUBMIT_REVIEWING_RESULT → FINISH` |
| 评审节点 | 模板化配置，运行时按评标办法实例化节点链 |
| 幂等主键 | 投标人同步以 `(tender_id, net_bid_id)` 为唯一键 |
| 文件策略 | 推送即归档到 `file` 服务，评标侧只存 `fileId` 和摘要 |
| 认证策略 | 专家前台使用 `EVALUATION` token；服务间调用使用 `INTERNAL` 能力 |
| 角色 | 专家（含组长标记）；无独立代理角色，招标人直接操作 EVAL_SETTING |
| 结果回传 | 通过 Interaction 机制回传业务系统 |
| 追踪 | 全链路透传 `X-Trace-Id`，MDC 键 `traceId` |

## 四、总体架构

### 4.1 数据流

```
                    ┌──────────────┐
                    │  业务系统     │
                    └──┬───────┬───┘
            专家名单推送│       │启动评标指令 / 接收结果回传
                       ▼       ▼
┌──────────┐  HTTP  ┌──────────────────┐  Interaction  ┌──────────────┐
│  crypto  │ ──────→│   evaluation     │ ─────────────→│  业务系统     │
│  :8083   │ 逐条推送│   :8084          │  结果回传      └──────────────┘
└──────────┘ 投标人  │                  │
                     │  ┌────────────┐  │  WebSocket  ┌─────────────────────┐
                     │  │ eval_ DB   │  │ ◄──────────→│ evaluation-frontend │
                     │  └────────────┘  │             │ :3001               │
                     └────────┬─────────┘             └─────────────────────┘
                              │ HTTP（内部凭证）
                              ▼
                     ┌──────────────┐
                     │  file :8081  │  (文件归档 / 代理下载)
                     └──────────────┘
```

### 4.2 不再保留的旧链路

一期不复制原系统中的以下能力：

- `evaluation → crypto` 的"反查招标文件版本"接口
- `evaluation → crypto` 的"按磁盘目录下载附件"接口

原因：crypto 推送前已完成归属和版本校验；v9 解密结果包含 `versionInfo`；评标所需附件同步时即归档到 `file` 服务。

### 4.3 数据来源映射

crypto 解密产物（v9 格式）到评标数据的对应关系：

| 评标所需数据 | v9 解密产物来源 |
|---|---|
| 项目/标段基本信息 | `baseInfo` |
| 投标人信息 | `bidLetter` |
| 标录方案和数据 | `bidForms`（`schemeContent` + `bidFormData`） |
| 评审规则树 | `bidEvalRules` |
| 投标人附件 PDF | 各评审分类的 `file` 字段（base64） |
| 版本和防篡改信息 | `versionInfo` |

剩余需业务系统/评标模块自行管理：
- 专家信息（业务系统通过 `sync/experts` 推送）
- 项目级配置（偏差阈值等，通过 `sync/start` 或 `EVAL_SETTING` 阶段设置）

## 五、认证与安全边界

### 5.1 Token 类型划分

| 场景 | 凭证类型 | 说明 |
|------|----------|------|
| 专家登录 evaluation 前端 | `EVALUATION` | 仅用于评标前台与评标后端 |
| 招标人操作 EVAL_SETTING | `INTERNAL` 或业务系统交互凭证 | 通过业务系统或管理端操作 |
| `crypto → evaluation` 内部推送 | `INTERNAL` | 服务间调用 |
| `evaluation → file` | `INTERNAL` | 评标后端代理文件访问 |
| `evaluation → interaction` 结果回传 | 内部服务能力 / 签名头 | 不透传专家 token |

### 5.2 安全原则

- `EVALUATION` token 只被 `ele-tender-evaluation` 接受
- 其他服务（`support` / `file` / `crypto`）不对 `EVALUATION` token 开放
- 评标后端访问其他服务必须使用内部凭证
- 所有内部同步接口要求登录、权限校验、记录 `traceId`
- 所有同步接口幂等，允许重放

## 六、状态设计（核心章节）

> **设计理由**：本章是 v3 相对 v1/v2 改动最大的部分。v2 凭空构造了 6 个节点内状态枚举（`PENDING → EXPERT_SCORING → EXPERT_CONFIRMED → LEADER_REVIEW → NODE_CONFIRMED → COMPLETED`），但核对原评标系统代码后发现，原系统从未使用节点状态枚举。原系统用的是**双标志位 + 专家个人进度**的组合模型，经过生产验证，逻辑简洁且支持重评/重置。v3 采用该模型。

### 6.1 项目生命周期

```
INIT(0) → EVAL_SETTING(1) → EXPERT_PREPARE(2) → REVIEWING(3) → SUBMIT_REVIEWING_RESULT(4) → FINISH(5)
```

| 阶段 | 含义 | 操作人 | 对应原系统 |
|------|------|--------|-----------|
| `INIT` | 项目已创建，正在接收投标人同步数据 | 系统（crypto 推送） | `INIT` |
| `EVAL_SETTING` | 投标人数据齐备，配置评标参数、确认专家 | 招标人 | `DELEGATE_SETTING`（原由代理操作） |
| `EXPERT_PREPARE` | 专家签到、组长选举 | 专家 | `EXPERT_PREPARE` |
| `REVIEWING` | 评审节点循环中 | 专家 + 组长 | `REVIEWING` |
| `SUBMIT_REVIEWING_RESULT` | 最终结果确认 | 组长 | `SUBMIT_REVIEWING_RESULT` |
| `FINISH` | 结果已回传，项目闭环 | 系统 | `FINISH` |

**与 v1/v2 的差异**：
- v1 为 5 阶段（`INIT → EXPERT_PREPARE → REVIEWING → SUBMIT_RESULT → FINISH`），缺少 `EVAL_SETTING`
- v2 为 7 阶段（`INIT → WAIT_EXPERT_SYNC → READY → REVIEWING → RESULT_CONFIRMED → CALLBACK_SUCCESS → FINISH`），拆分过细且无原系统对照
- v3 为 6 阶段，与原系统一一对应，仅将 `DELEGATE_SETTING` 改名为 `EVAL_SETTING`

**保留 `EVAL_SETTING` 的理由**：
原系统中 `delegateStart()` 在此阶段执行关键操作——初始化评审节点链（从模板实例化副本）、设置首节点 round=1、推进到 `EXPERT_PREPARE`。去掉此阶段会导致这些业务逻辑无处安放。

### 6.2 专家阶段

```
INIT(1) → ELECTION(2) → REVIEWING(3) → FINISH(4)
```

每个专家在 `eval_project_expert` 表中有独立的 `stage` 字段。

| 阶段 | 含义 |
|------|------|
| `INIT` | 准备阶段（已签到，等待选举） |
| `ELECTION` | 组长选举中 |
| `REVIEWING` | 评审中 |
| `FINISH` | 评标完成 |

与原系统 `ExpertStageEnum` 完全一致。

### 6.3 评审节点状态：双标志位模型

> **这是 v3 最核心的设计决策。**

每个评审节点实例（`eval_review_node`）不使用单一状态枚举，而是用两个标志位的组合来表达状态：

```
+----------+-----------------+------------------------------------------+
| summary  | summary_result  | 含义                                     |
+----------+-----------------+------------------------------------------+
|    0     |       0         | 评审中：专家正在打分/提交/确认             |
|    1     |       0         | 已汇总：组长已触发汇总计算，待确认汇总结果 |
|    1     |       1         | 已确认：汇总结果已确认，可推进下一节点      |
+----------+-----------------+------------------------------------------+
```

附加字段：
- `round`：当前轮次，重评/重置时递增
- `skip`：是否跳过（某些评标办法下部分节点可直接跳过）

**为什么不用线性枚举**：

| 对比项 | 线性枚举（v2 方案） | 双标志位（v3/原系统方案） |
|--------|---------------------|--------------------------|
| 重评操作 | 需定义回退跃迁规则 | 清零两个标志位即可 |
| 跳过节点 | 需特殊状态或跳过标记 | 直接设 summary=1, summaryResult=1, skip=1 |
| 状态机复杂度 | 6 状态 × 多种跃迁 = 复杂 | 2 × 2 = 4 种组合，逻辑简单 |
| 汇总与确认解耦 | 枚举中必须拆为两个状态 | 天然独立，互不干扰 |
| 生产验证 | 未经验证 | 原系统已在生产运行 |

### 6.4 专家节点内进度

每个专家在当前节点的进度由 `done` 字段追踪：

```
INIT(0) → SUBMIT(1) → CONFIRM_SUBMIT(2)
```

| 状态 | 含义 |
|------|------|
| `INIT` | 未提交（正在评审） |
| `SUBMIT` | 已提交评审结果 |
| `CONFIRM_SUBMIT` | 已确认提交（不可再修改） |

与原系统 `ExpertDoneStatusEnum` 完全一致。

**推进下一节点时，所有专家的 `done` 被重置为 `INIT`。**

### 6.5 节点内完整操作流程

```
1. [各专家] 评审并提交        → expert.done = SUBMIT
2. [各专家] 确认提交          → expert.done = CONFIRM_SUBMIT
3. [组长]   触发汇总          → 校验全员 CONFIRM_SUBMIT → 计算汇总 → node.summary = 1
4. [组长]   查看汇总结果
5. [组长]   确认汇总 / 要求重评
   ├─ 确认汇总               → node.summary_result = 1
   └─ 要求重评               → 重置 node.summary=0, 全员 expert.done=INIT
6. [组长]   推进下一节点      → 校验 summary_result=1 → 初始化下一节点 → 重置全员 done=INIT
```

**与 v1 的差异**：v1 笼统描述为"专家各自评审 → 专家确认提交 → 组长查看汇总 → 组长确认 → 推进下一节点"，本质正确但缺少"汇总"和"确认汇总"是两步独立操作的关键细节。

**与 v2 的差异**：v2 将此流程硬编码为 6 个节点状态枚举，v3 改为双标志位 + 专家 done 状态的组合，更灵活。

### 6.6 评审类型

每个节点有 `evaluation_system` 字段，区分两种评审类型：

| 类型 | 值 | 汇总逻辑 | 典型节点 |
|------|---|---------|---------|
| 通过制 | `PASS(1)` | 半数以上通过则判定通过 | 资格审查、符合性评审 |
| 打分制 | `SCORE(2)` | 去掉最高最低取平均（≥3 专家时） | 资信、技术、商务评审 |

原系统中 `CommonReviewFunctionService.passSummary()` 和 `scoreSummary()` 分别处理两种类型。

## 七、评审流程设计

### 7.1 评审节点模板化

> **设计理由**：原系统中评审节点不是写死的，而是按评标办法预配置的模板。`ReviewBidFlowNodeDomain` 是模板表，开启评标时（`delegateStart()`）将模板实例化为 `TenderReviewBidFlowNodeDomain` 副本绑定到具体项目。v3 沿用此设计。

节点模板表 `eval_review_node_template`：

| 字段 | 含义 |
|------|------|
| `method_id` | 所属评标办法 |
| `method_sign` | 评标办法标识 |
| `node_sign` | 节点标识（如 `qualifications`、`fix`、`credit`） |
| `node_name` | 节点名称 |
| `evaluation_system` | 评审类型：1=通过制, 2=打分制 |
| `index_of` | 排序序号 |
| `view_sign` | 前端视图标识 |
| `go_next_behavior` | 进入下一节点的行为策略 |

一期预置的两种评标办法节点链：

**最低评标价法**：
```
qualifications(PASS) → fix(PASS) → detail(PASS) → result
```

**综合评分法**：
```
qualifications(PASS) → fix(PASS) → credit(SCORE) → tec(SCORE) → business(SCORE) → result
```

原系统还支持 `price_correction`（报价修正）、`select_bidder`（入评单位确定）、`business_score`（商务打分）、`offer_price`（报价单）、`comprehensive`（综合评审）等节点类型，一期不纳入但架构预留。

### 7.2 开启评标（EVAL_SETTING → EXPERT_PREPARE）

对应原系统 `AbstractUMethodManager.delegateStart()`，操作人从代理改为招标人：

1. 校验项目处于 `EVAL_SETTING` 阶段
2. 校验评标时间已到达
3. 从节点模板表实例化节点链副本，绑定到当前项目
4. 设置首节点 `round = 1`
5. 所有节点 `summary = 0, summary_result = 0`
6. 初始化投标人过滤列表
7. 设置所有专家阶段为 `INIT`
8. 项目阶段推进到 `EXPERT_PREPARE`，轮次设为 1

### 7.3 进入评审（EXPERT_PREPARE → REVIEWING）

对应原系统 `ExpertElectionService.enterReview()`：

1. 组长选举完成后，由组长触发
2. 设置所有专家阶段为 `REVIEWING`
3. 重置全员 `done = INIT`
4. 项目 `nodeSign` 设为第一个评审节点（`qualifications`）
5. 项目阶段推进到 `REVIEWING`

### 7.4 推进下一节点

对应原系统 `CommonReviewFunctionService.gotoNextFlowNodeNormal()` 等方法：

1. 校验当前节点 `summaryResult = 1`
2. 创建下一节点的投标人过滤列表（排除当前节点淘汰的投标人）
3. 设置下一节点的 `round`
4. 重置全员 `done = INIT`
5. 更新项目 `nodeSign` 到下一节点
6. 触发 `afterGotoNextFlowNode` 钩子（如到达 `result` 节点时创建最终结果）

### 7.5 重评与重置

原系统支持两种回退机制，一期均保留：

**重评（当前节点）**：
- 组长发起
- 重置全员 `done = INIT`
- 清除当前节点 `summary = 0, summaryResult = 0`
- 删除已有汇总结果
- WebSocket 通知全员刷新

**重置（回退到之前节点）**：
- 管理操作（组长或招标人）
- 清除目标节点到当前节点之间所有节点的状态（summary、summaryResult、round）
- 重置全员 `done = INIT`
- 项目 `nodeSign` 回退到目标节点
- 项目 `round` 递增
- 记录重置日志

### 7.6 少于三家

一期保留"少于三家投票"能力，触发口径：

- 在项目正式进入首个评审节点前
- 按"已成功同步并进入评标名单的投标人数"判断
- 若数量 `< 3`，触发投票

投票选项：继续评标 / 废标 / 重新招标。一期不在后续节点中重复触发。

## 八、同步协议设计

### 8.1 统一约束

- 内部同步接口前缀统一为 `/api/eval/internal/*`
- 返回结构统一为 `Result.success(data)` / `Result.fail(code, msg)`
- 所有请求透传 `X-Trace-Id`
- 所有写接口必须幂等

### 8.2 投标人同步

`POST /api/eval/internal/sync/bidder`

crypto 解密成功后逐条推送。

请求体：

```json
{
  "tenderId": "td-001",
  "netBidId": "nb-001",
  "enterpriseId": "ent-001",
  "decryptSort": 1,
  "isUnion": 0,
  "enterpriseIsUnion": 0,
  "payloadSha256": "sha256-of-normalized-payload",
  "payload": {
    "baseInfo": {},
    "tender": {
      "bidLetter": {},
      "bidForms": {},
      "bidEvalRules": {}
    },
    "versionInfo": {}
  }
}
```

处理规则：

- 唯一键：`(tenderId, netBidId)`
- 首次接收：创建 `eval_project`（若不存在）、`eval_bidder` 及相关快照
- 重复接收且 `payloadSha256` 相同：幂等成功
- 重复接收但 `payloadSha256` 不同：
  - 项目处于 `INIT` / `EVAL_SETTING` 时允许覆盖，写入 `eval_sync_log`
  - 项目已进入 `EXPERT_PREPARE` 及之后阶段：拒绝覆盖，返回业务失败码

### 8.3 专家名单同步

`POST /api/eval/internal/sync/experts`

业务系统推送项目专家名单。

请求体：

```json
{
  "tenderId": "td-001",
  "experts": [
    {
      "expertId": "exp-001",
      "expertName": "张三",
      "mobile": "13800000000",
      "identityNo": "3301************",
      "leaderFlag": false
    }
  ]
}
```

处理规则：

- 按 `tenderId + expertId` 幂等 upsert
- 项目已开始评审（`REVIEWING` 及之后）不允许删除已在场专家
- 组长可通过名单同步直接指定，也可通过选举产生；两者冲突时以显式指定优先

### 8.4 启动指令

`POST /api/eval/internal/sync/start`

通知 evaluation 项目数据齐备，可进入 `EVAL_SETTING`。

请求体：

```json
{
  "tenderId": "td-001",
  "expectedBidderCount": 5,
  "allowMissingSyncedBidder": false,
  "deviationThresholdPercent": 20,
  "triggerUserId": "system",
  "triggerUserName": "系统",
  "remark": "评标准备完成"
}
```

处理规则：

- `expectedBidderCount` 用于校验数据是否齐备
- `allowMissingSyncedBidder = false` 时：`已同步投标人数 == expectedBidderCount` 才允许项目进入 `EVAL_SETTING`
- `allowMissingSyncedBidder = true` 时：允许以当前已同步集合继续，记录原因
- 收到启动指令后项目从 `INIT` 推进到 `EVAL_SETTING`
- 已处于 `EVAL_SETTING` 或更后阶段时按幂等成功处理

### 8.5 结果回传

评标结果通过 Interaction 机制回传业务系统。

一期新增 DTO：

- `EvaluationResultCallbackRequest`
- `EvaluationBidderResultItem`
- `EvaluationNodeSummaryItem`

最小回传字段：

- `projectId` / `tenderId` / `bidEvalMethod`
- `winnerEnterpriseId` / `winnerEnterpriseName`
- `rankingList`（含每个投标人排名、得分、淘汰节点等）
- `nodeSummaries`（各节点汇总摘要）
- `traceId`

## 十、文件处理策略

采用"推送即归档"方案，不沿用原系统磁盘直链下载：

1. `crypto` 将 v9 payload 推给 `evaluation`
2. `evaluation` 从 payload 中提取 base64 文件内容
3. `evaluation` 调用 `file` 服务上传文件
4. `evaluation` 仅保存 `fileId / fileSha256 / fileName / fileSize`
5. 前端访问 `evaluation` 文件代理接口，后端用内部凭证读取 `file`

原因：复用现有文件服务；统一下载鉴权和审计；消除磁盘目录耦合。

| 设计点 | v1 | v2 | v3 |

| 项目生命周期 | 5 阶段，缺 EVAL_SETTING | 7 阶段，无原系统对照 | 6 阶段，与原系统一一对应 |
| 节点状态模型 | 未详细设计 | 6 状态线性枚举（凭空构造） | 双标志位（summary + summaryResult），来自原系统 |
| 专家节点内进度 | 未区分 | 未区分 | INIT → SUBMIT → CONFIRM_SUBMIT，来自原系统 |

| 评审节点配置 | 写死两种办法 | 写死两种办法 | 模板化，运行时实例化 |
| 评审类型 | 提到 PASS/SCORE | 未区分 | 明确 PASS(1)/SCORE(2)，汇总逻辑不同 |
| 重评/重置 | 未涉及 | 未涉及 | 完整支持，参考原系统 |
| 架构图 | ASCII 数据流（清晰） | 文本列表（退化） | 恢复 ASCII 数据流 |
| 数据来源映射 | 有（Section 9） | 丢失 | 恢复（Section 4.3） |

| 参考边界 | "参考现有系统"（过宽） | 明确（Section 2） | 进一步明确到具体代码文件 |

| 投标人过滤列表 | 未涉及 | 未涉及 | 新增 eval_bidder_filter，按节点追踪参评投标人 |

## 十五、结论

v3 的核心改进是**用原系统验证过的状态模型替换凭空设计的枚举**：

- 节点状态用 `summary + summaryResult` 双标志位，而非线性枚举
- 专家进度用 `done`（INIT/SUBMIT/CONFIRM_SUBMIT）独立追踪
- 项目生命周期与原系统一一对应，仅将 DELEGATE_SETTING 改名 EVAL_SETTING
- 评审节点模板化，一期预置两种评标办法，架构支持扩展

同时保留了 v1 的架构可视化和数据来源映射，保留了 v2 的幂等设计和同步协议完整度。

关键原则：**参考原系统的状态模型和业务规则，使用 EleTender 的技术基线和公共设施，不搬迁代码。**
