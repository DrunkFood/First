# 原始解密系统 (information-biddingfile-decrypt) 分析报告

## 1. 项目概述

这是一个**纯后端** Spring Boot 服务，无前端。核心功能是：轮询数据库中待解密的投标文件，执行解密、解析、校验，然后将结构化数据推送给评标系统。

- **端口**: 8018
- **数据库**: 达梦 DM8（国产信创）
- **注册中心**: Nacos
- **服务间调用**: Spring Cloud OpenFeign
- **认证框架**: Sa-Token

---

## 2. 核心架构：生产者-消费者 + 双层并发控制

```
┌─────────────────────────────────────────────────────────────────┐
│                      系统启动 (CommandLineRunner)                 │
│                                                                  │
│  ┌──────────────────────┐    ┌────────────────────────────────┐  │
│  │ TendersTaskAcquire   │    │ TendersTaskHandle              │  │
│  │ Manager (生产者线程)  │    │ Manager (消费者线程)            │  │
│  │                      │    │                                │  │
│  │ 轮询 DB → 查待解密   │    │ Semaphore 控制最大并发标段数    │  │
│  │ 标段 → 放入阻塞队列  │───→│ FixedThreadPool 分派任务       │  │
│  │                      │    │                                │  │
│  │ sleep(有任务10s/     │    │  ┌─ OneTenderTaskHandler ──┐   │  │
│  │       无任务10s)     │    │  │ 内部 Semaphore + Pool   │   │  │
│  └──────────────────────┘    │  │ 单标段并发解密多条记录  │   │  │
│                              │  └─────────────────────────┘   │  │
│                              └────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────┘
```

**并发参数**（可配置）：
- `each-acquire-tender-max-count`: 同时处理的最大标段数（默认 1）
- `each-tender-max-handle-bid-record-thread-count`: 单标段并发解密线程数（默认 2）

## 3. 单条投标文件完整处理流程

```
BiddingFileHandlerProcessor.handle(netBidRecord)
│
├── 1. checkEnterprise()
│   └── Feign 调主体服务 → 获取企业详情
│
├── 2. decryptBidEncrypt()  【第一层解密：TSign SDK】
│   ├── 查 ENCRYPT_FILE 表 → 获取 encryptedKey、加密文件名、源 MD5
│   ├── FileDecryptUtils.decryptFileEx(加密文件, 解密输出, key)
│   ├── MD5 校验（解密文件 vs 源 MD5）
│   └── 成功 → FILE_DECRYPT_STATE = 2
│
├── 3. handleSelfMadeBiddingFile()  【第二层解密：AES-CBC，仅综合交易】
│   ├── AES/CBC/PKCS5Padding 解密 .decrypt → .origin (JSON)
│   └── afterDecryptSelfBidDocument()
│       ├── JsonBidDocumentProcessor.analysis() — 流式解析 JSON
│       ├── 校验标段归属（tenderNo）
│       ├── 校验招标文件版本号
│       ├── 校验企业名与主体库匹配
│       ├── 校验联合体成员
│       ├── 写 OPENBID_RECORD + OPENBID_RECORD_TEMP
│       └── 推送评标系统（Feign + Redis 备份 TTL 24h）
│
└── 4. signEnterprise()
    ├── 写 OPENBID_SIGN（后台签到）
    └── 联合体 → 写 OPENBID_UNION_SIGN
```

## 4. 双层解密算法

| 层次 | 算法 | 密钥来源 | 适用范围 |
|------|------|---------|---------|
| 第一层 | TSign SDK (`FileDecryptUtils.decryptFileEx`) | `ENCRYPT_FILE.ENCRYPTED_KEY`（CA 体系生成） | 所有投标文件 |
| 第二层 | AES/CBC/PKCS5Padding (Hutool) | 配置文件 `originEncryptKey` + `originEncryptIv` | 仅综合交易 (ZHJY5) |

## 6. 数据库核心表

| 表名 | 用途 |
|------|------|
| `NET_BID` | 投标记录主表，状态机核心（FILE_DECRYPT_STATE: 0待处理→1解密中→2成功→3失败） |
| `ENCRYPT_FILE` | 加密文件记录（encryptedKey, 文件名, 源MD5） |
| `TENDER` | 标段表 |
| `PROJECT_ARRANGEMENT` | 包段/安排表（含开标时间） |
| `NET_OPENBID_PROCESS` | 开标进程控制 |
| `OPENBID_RECORD` / `OPENBID_RECORD_TEMP` | 开标标录（结构化报价数据） |
| `OPENBID_SIGN` / `OPENBID_UNION_SIGN` | 企业签到 |
| `OPENBID_QUEUE` | 开标直播队列 |
| `COMMON_MAIN_RECORD` | 招标文件版本记录 |

**乐观锁争抢**：`UPDATE NET_BID SET FILE_DECRYPT_STATE=1 WHERE ID=? AND FILE_DECRYPT_STATE=0`，影响行数=1才算抢到。

**多实例分片**：`DEPLOY_CONFIG_ID` 字段标识任务归属哪个解密节点。

## 10. 设计亮点

1. **双层 Semaphore** 精细化并发控制（标段级 + 记录级）
2. **DEPLOY_CONFIG_ID 分片**实现多实例横向扩展
3. **CAS 乐观锁**防并发重复处理
4. **JsonReader 流式解析**大文件内存友好
5. **错误处理分阶段**（解密前/解密后），保证签到等关键操作不遗漏

## 11. 技术债

1. 测试代码混在生产代码中（`TestService`、`MainThreadCreator` 内 `createTestData`）
2. `TGSignHttpPostBuilder` 历史遗留，未使用
3. 密钥明文配置在 `application-local.yaml`
4. `FILE_DECRYPT_STATE=1`（解密中）无超时恢复机制，服务崩溃会导致记录永久卡住
5. 无单元测试

## 12. 现仓库 crypto 实现对照补充（2026-03-31）

当前 `ele-tender-crypto` 落地过程中，基于 code review 与仓库实现核对，补充以下结论：

### 12.1 已确认问题

1. `CryptoFingerprintUtil` 当前仅对 `bidderPwdStr` 做 SHA-256，未使用 `bidderPwdFingerprintSecret`。
2. `BidDocumentServiceImpl` 当前文件落盘路径为 `{basePath}/{appKey}/{sha256}.HzctTbs`，尚未补齐三级子目录。
3. `bdc_bid_document.file_id` 当前在 DDL 中为 `bigint`，`BdcBidDocument.fileId` 与 bid-document push/callback DTO 也仍为 `Long`，与 `varchar(64)` 规范不一致。

### 12.2 已收敛但暂不直接改动的问题

1. `DecryptTaskStreamConsumer` 的 `finally ACK` 属于当前主动设计，不直接视为遗漏；真正风险是异常时状态落库失败可能造成消息丢失窗口。
2. 默认配置下 `passwordCacheSeconds` 大于 `taskTimeoutSeconds`，不存在“超时重试必然失败”的结论。
3. `BidDocumentServiceImpl` 的查重维度与 artifact 复用维度不同，是否增加唯一键需先确认业务语义。
4. `retryRequest` 当前不会让已终态 request 再次进入回调流程，原“触发其他 request 重复回调”结论不成立。
