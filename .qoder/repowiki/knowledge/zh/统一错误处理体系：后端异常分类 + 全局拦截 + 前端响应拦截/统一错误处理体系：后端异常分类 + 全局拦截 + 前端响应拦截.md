## 错误处理架构概览

该项目采用分层统一的错误处理机制，后端基于 Spring Boot 的 @RestControllerAdvice 实现全局异常捕获，前端通过 Axios 拦截器统一处理 HTTP 响应和认证状态。

## 后端错误处理体系

### 1. 统一响应格式
所有接口返回统一的 Result<T> 结构体，包含 code（业务状态码）、message（用户友好的错误消息）、data（响应数据）、timestamp（时间戳）。

### 2. 异常类型层次结构
在 ele-ai-tender-common 模块中定义了标准化的异常类：
- BusinessException: 通用业务异常，支持自定义错误码
- AuthException: 认证授权相关异常（未登录、权限不足等）
- AiUnavailableException: AI服务不可用异常
- FileException: 文件操作异常
- AiErrorContentException: AI内容处理异常

每个异常类都继承自 RuntimeException，并包含 code 字段用于映射到具体的业务错误码。

### 3. 全局异常处理器
每个微服务模块都有独立的 GlobalExceptionHandler：

核心服务处理器 (ele-ai-tender-core/handler/GlobalExceptionHandler.java)：
- 统一捕获 AuthException、BusinessException
- 处理参数校验异常：MethodArgumentNotValidException、BindException
- 处理HTTP协议异常：HttpMediaTypeNotSupportedException、HttpMessageNotReadableException
- 兜底捕获所有未处理异常

AI服务处理器 (ele-ai-tender-ai/handler/GlobalExceptionHandler.java)：
- 额外处理 AiUnavailableException
- 提供更详细的系统异常信息

### 4. 错误码规范
ResponseCode 枚举按业务域划分错误码段：
- 1xxx: 用户相关
- 2xxx: 角色权限相关
- 3xxx: 接入系统相关
- 4xxx: 版本管理相关
- 5xxx: 文件相关
- 7xxx: 加解密相关
- 8xxx: AI编制系统相关（项目、需求、模板、评审项等）
- 9xxx: 系统参数、政策文件、消息等

## 前端错误处理机制

### 1. Axios 响应拦截器
两个前端应用都实现了统一的请求拦截器：

主业务前端 (ele-ai-tender-frontend/src/utils/request.ts)：
- 自动添加 Bearer Token 到请求头
- 统一处理 401 未授权状态，弹出确认框后登出
- 防止重复弹窗的状态锁机制
- 对 blob 响应（文件下载）特殊处理

支撑管理前端 (ele-ai-tender-support-frontend/src/utils/request.ts)：
- 更详细的 HTTP 状态码处理（400/401/403/404/500）
- 网络超时和连接错误的友好提示
- 路由跳转和登出逻辑

### 2. 错误展示策略
- 使用 Element Plus 的 ElMessage.error() 显示错误消息
- 认证过期使用 ElMessageBox.confirm() 进行用户确认
- 业务错误直接显示后端返回的 message
- 网络错误提供通用的友好提示

## 设计原则与约定

### 1. 异常传播规则
- 业务层抛出具体异常类型，而非裸字符串
- 控制器层不捕获业务异常，交由全局处理器统一处理
- 避免在业务方法中使用 try-catch 包裹业务逻辑

### 2. 错误码使用规范
- 优先使用 ResponseCode 枚举中的预定义错误码
- 新增错误码需遵循分片规则，避免冲突
- 业务异常构造时传入 ResponseCode 对象而非硬编码数字

### 3. 前后端协作约定
- 前端统一通过 Result.code === 200 判断成功
- 401 状态码统一触发登出流程
- 其他业务错误码由前端直接展示 message

### 4. 日志记录规范
- 所有异常处理都记录 ERROR 级别日志
- 包含完整的异常堆栈信息
- 区分业务异常和系统异常的日志前缀

这种分层错误处理机制确保了错误的一致性、可追溯性和用户体验的统一性。
