本仓库在后端采用分层异常类型、全局异常处理器和统一响应体的三层架构，贯穿 ele-ai-tender-common、core、ai、support、interaction 等所有 Spring Boot 子模块。

## 1. 系统/模式概览
- 统一响应体：com.jy.eleaitender.common.response.Result<T> 作为所有 REST 接口的标准返回结构，包含 code、message、data、timestamp，并提供 success() / fail(code, message) 等静态工厂方法。
- 状态码枚举：com.jy.eleaitender.common.enums.ResponseCode 集中定义全平台错误码（200/400~499/用户 1xxx/文件 5xxx/加解密 7xxx/AI 8xxx/系统参数 9xxx 等），业务异常通过该枚举绑定语义化 code。
- 分层运行时异常：在 common 包下按领域拆分异常类，均继承 RuntimeException 并持有 int code，由各自的全局处理器统一捕获并转为 Result.fail(...).

## 2. 核心文件与位置
- 统一响应体与状态码
  - ele-ai-tender-system/ele-ai-tender-common/src/main/java/com/jy/eleaitender/common/response/Result.java
  - ele-ai-tender-system/ele-ai-tender-common/src/main/java/com/jy/eleaitender/common/enums/ResponseCode.java
- 通用异常基类族
  - BusinessException — 通用业务异常
  - AuthException — 认证/鉴权异常
  - AiUnavailableException — AI 模型不可用
  - AiErrorContentException — AI 输出内容解析失败（附带原始 content）
  - FileException — 文件上传/校验异常
  - InteractionException（interaction 子模块）— 第三方交互层异常，使用 InteractionResponseCode
- 各服务全局异常处理器（@RestControllerAdvice）
  - ele-ai-tender-system/ele-ai-tender-ai/src/main/java/com/jy/eleaitender/ai/handler/GlobalExceptionHandler.java
  - ele-ai-tender-system/ele-ai-tender-core/src/main/java/com/jy/eleaitender/core/handler/GlobalExceptionHandler.java
  - support、file 等模块遵循相同模式

## 3. 架构与约定
- 异常抛出规范
  - 业务校验失败 → throw new BusinessException(ResponseCode.XXX, "具体消息")
  - 认证失败 → throw new AuthException(...)
  - AI 路由不可用 → throw new AiUnavailableException(...)
  - 文件 I/O 失败 → throw new FileException(...)
  - 第三方交互失败 → throw new InteractionException(InteractionResponseCode.FAIL, ...)
- 全局处理器职责
  - 将上述异常映射为 Result.fail(code, message)，HTTP 状态码统一返回 200，由前端根据 code 判断成功/失败。
  - 对 Spring 框架异常（MethodArgumentNotValidException、BindException、HttpMediaTypeNotSupportedException、HttpMessageNotReadableException）统一转成 PARAM_ERROR 并拼接字段级错误信息。
  - 兜底 Exception.class 处理器记录堆栈日志并以固定文案或带 detail 的文案返回，避免把内部堆栈泄露给客户端。
- AI 特有流程
  - AI 生成器中若 LLM 返回 JSON 解析失败，会抛出 AiErrorContentException，携带原始 content，便于上层记录调试信息。
  - 模型路由选择失败时抛 AiUnavailableException，由 AI 模块全局处理器包装为友好提示。

## 4. 前端侧配合
- 前端 utils/request.ts 基于 axios 拦截器，统一读取后端 Result.code，非 200 时触发全局错误提示（如 ElMessage.error）。
- 局部 catch 仅用于 UI 容错（自动保存、反馈提交等），不吞掉业务错误码。

## 5. 开发者应遵守的规则
1. 禁止直接返回裸异常或 HTTP 5xx：所有接口必须通过 Result.success/fail 返回；业务异常一律 throw 自定义异常类。
2. 优先使用 ResponseCode 枚举：不要手写硬编码数字码，新增场景先在 ResponseCode 中申请新码段。
3. 异常类只承载 code + message + cause：不要在异常里塞大对象，详情走日志或 Result.data。
4. 全局处理器未覆盖的异常会被兜底：新增领域异常需同步在对应模块的 GlobalExceptionHandler 中添加 @ExceptionHandler。
5. AI 相关错误区分不可用和内容异常：模型连通性失败用 AiUnavailableException，LLM 输出格式问题用 AiErrorContentException。
6. 第三方交互异常使用 InteractionException：保持 interaction 模块独立的状态码空间。
