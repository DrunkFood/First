## 1. 系统/方法
- 基于 Spring Boot @RestControllerAdvice + @ExceptionHandler 的全局异常处理，每个后端子模块（core、ai、file）各自维护一个 GlobalExceptionHandler；interaction SPI 提供独立的 InteractionAiGlobalExceptionHandler 用于回调接口。
- 统一响应体为 Result<T>，所有业务错误通过抛出带 code/message 的自定义异常，再由全局处理器转为 Result.fail(...) 返回，HTTP 状态码始终为 200，由前端根据 code 判断成功/失败。
- 统一的错误码枚举 ResponseCode 集中管理所有业务错误码，覆盖通用、用户、权限、文件、AI、项目、需求、模板、评审项、版本、知识库、检测、模型配置、系统参数、政策文件、消息、模型路由、文档集成等域。

## 3. 架构与约定
- 异常分层：
  - 认证类：AuthException，默认 UNAUTHORIZED(401)。
  - 业务类：BusinessException，默认 FAIL(500)。
  - 领域扩展：AiUnavailableException、FileException、AiErrorContentException、AiSyncedException 等，均内嵌 code 字段并默认映射到 ResponseCode.FAIL，便于在业务层直接抛出自定义码。
- 全局处理器职责：
  - 将 AuthException、BusinessException、AiUnavailableException、FileException 等已知异常转换为 Result.fail(code, message)，并记录 ERROR 日志。
  - 对 Spring 校验异常（MethodArgumentNotValidException、BindException）、媒体类型/请求体解析异常统一归并为 PARAM_ERROR(400) 并拼接字段级错误信息。
  - 兜底 Exception 分支：core/file 使用“系统异常: <detail>”，ai 模块进一步封装，核心原则是不向客户端暴露内部堆栈或 SQL 片段（见单元测试断言）。
- 交互层隔离：interaction SPI 的 InteractionAiGlobalExceptionHandler 仅作用于 InteractionAiTaskResultCallbackController 所在包，返回 InteractionResult，避免与主站 Result 混用。
- 非 HTTP 路径：异步任务处理器（如 AiTaskProcessor）中通过 catch (AiUnavailableException | AiErrorContentException | TimeoutException) 显式区分可重试/不可重试场景，并在外层更新任务状态，而非直接向上抛出。

## 4. 开发者应遵循的规则
- 禁止直接返回裸异常或 throw RuntimeException：业务侧应优先抛 BusinessException(ResponseCode.XXX, ...) 或对应领域异常，让全局处理器统一包装。
- 错误码必须来自 ResponseCode：新增错误码时先在枚举中登记，再在异常构造器中使用，避免硬编码数字。
- 不要向客户端泄露内部细节：全局处理器已屏蔽 SQL/堆栈，业务代码也不应在 message 中携带敏感信息。
- 校验异常走 Bean Validation：Controller 入参使用 @Valid/@Validated，由全局处理器自动聚合字段错误为 field: msg; field2: msg2 格式。
- 跨服务调用异常：内部 RPC/HTTP 调用（如 InternalFileServiceClient）应将底层异常包装为 BusinessException/FileException 后再抛出，不要在 client 层直接抛 RuntimeException。
- 异步任务异常分类：在任务执行链路中按 AiUnavailableException、AiErrorContentException、TimeoutException 等分别处理，确保任务状态机正确推进。
- interaction 回调接口：如需新增回调 Controller，请在 interaction-autoconfigure 中复用 InteractionAiGlobalExceptionHandler，并使用 InteractionResult 作为返回体。
